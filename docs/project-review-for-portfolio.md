## 0. 结论先行

**这个项目的卖点不是"我写了个爬虫 Agent"。** 如果这么讲，面试官会归到"用过 Playwright"一类，然后忘掉。

你真正的技术含量在另一件事上：

> **一个代替用户对外执行动作（投递简历）的 Agent，如何做到"不越权、不重复、可解释、失败可收敛"。**

这是一个**有真实约束的分布式副作用问题**：点击一旦发出，结果可能未知；进程可能重启；用户可能在浏览器里手动操作；授权只能用一次。你在这上面解决的问题，比"能跑通流程"值钱得多。

按这个定位衡量，当前的**需求和实现已经基本闭环**，但有 **3 个环节存在实测断点**，另有 **2 项工程基建缺失**会让面试官当场减分。补齐成本不高，收益很大。

## 2. 需求和实现是否闭环？逐个环节实测

闭环链条：

```
用户指令 → 意图与槽位 → 规划 → 搜索发现 → JD 抓取 → 匹配评分
        → 授权 → 沟通 → 检测回复 → 投递 → 看板状态 → 复盘产物（总结/成长计划）
```

| 环节 | 状态 | 证据 / 断点 |
|---|---|---|
| 意图与槽位 | ✅ 闭环 | `search_parse` 正确产出 `{result_limit, salary_min, locations}` |
| 规划与授权校验 | ✅ 闭环 | 三步骤计划生成正确，未授权工具被拒 |

| JD 抓取与评分 | ✅ 可跑 | 未在本轮端到端测量（**未测**） |
| 授权与预览 | ✅ 闭环 | 一次性授权、绑定校验、竞态保护 |

## 2.5 ⚠️ 独立代码审查发现的「不可达子系统」——面试最大风险点

一次独立静态审查（AST + 全仓引用扫描）发现**三个对外宣称的子系统没有任何入口**。这不是普通 bug：**面试官 grep 一下就会发现前端有 UI、后端分支却永远走不到。**

| # | 子系统 | 为什么不可达 | 连带失效 |
|---|---|---|---|
| **D2** | **原生 tool-calling 循环** | 入口要求 `checkpoint.phase=="tool_loop"`（`main_agent.py:649`），而该值**只由这个循环自己写入**（`:1240`），且只能经 `resume_checkpoint`（`manager.py:217,822`）到达，而 `resume` 又用它作为放行条件（`:818`）→ **无引导路径** | 流式输出通道、4 个 context 工具、tool-loop 的**安全上限全部失效**（每次调用都新建 `ToolLoopState()`） |
| **D3** | **澄清（clarify）交互** | `IntentRouter._clarify_outcome`（`router.py:239`）是 `clarify` 决策的**唯一生产者，且从未被调用** | `clarify_memory` 永远为空、`main_agent.py:821-830` 分支死代码，而**前端 `page.tsx:1850-1855` 有完整可点的澄清按钮** |
| **D1** | **失败启动恢复** | `checkpoint='failed_before_submit'` **只有读取方没有写入方**（我引入的回归，已修 `90ef755`） | 优先级 90 规则永不匹配、恢复计数器恒为 0 |

> **D1 是我在本次会话中引入的**：我把写入值改成 `retry_exhausted`，于是查询永远返回空、整个恢复子系统静默消失。**已修复**，并新增优先级 95 的 `escalate_exhausted_start` 处理"预算用尽"的情形。

**这三个必须处理，二选一：**

- **删掉**（推荐用于 D2/D3）：删掉不可达代码 + 删掉对应前端 UI。**面试时"我删掉了走不通的路径"比"我写了但走不通"强得多。**
- **接通**：补引导路径，让它真的能进得去。

**千万别留着不动**——这是唯一会让面试官直接质疑"你到底有没有跑过自己写的功能"的问题。

### 安全机制方面：审查给出的正面结论

审查**独立确认**了这套安全设计是扎实的，可以作为面试重点：

- **OS 级浏览器租约**，两个 worker 共用同一路径，崩溃由 OS 释放，无 PID 探测/杀进程；
- **简历投影按摘要绑定**，在点击前**最后一次**重新校验（`delivery/automation.py:374,380`）；
- **点击一次后只做核对、绝不第二次点击**（`delivery/mock_site_adapter.py:278-295` 故意吞掉点击异常，只认站点正向证据）；
- **从 `classify_failure` 的 `uncertain` 标志到 `outcome_indeterminate` 的 fail-closed 链路一致**；
- API Key 常量时间比较、请求体限制、读写分离限流、安全响应头、JSONL 审计、**每个持久化边界都做 PII/密钥脱敏**。

## 3. 能不能讲出原因？——三个能撑住追问的因果链

面试官会追问"为什么"。下面三条你已经有一手证据，**建议背下来**。

### 3.1 一个"尽力而为的提取器"拥有否决权（最漂亮的 bug）

**现象**：复合请求被拒，报"城市条件不能完整解析"。

**根因**：`explicit_search_constraints()` 语义上是**尽力而为的抽取器**，但它在 `plan_request()` 关键路径上**带 `raise`**。8 个调用点里，**只有 1 个**包了 try/except。于是解析不确定 → 抛异常 → **LLM 规划器根本没被调用**。

**为什么值钱**：这不是"提示词没写好"，而是**契约设计错误**——把"提取器"和"校验器"两种职责混在一个函数里。修法是把抽取器改成**非否决式**（不确定的片段通过 `unresolved` 上报，交给模型判断），真正的冲突（`数量15个` + `数量20个`）仍然 fail-closed。

**可以补一句**：这个 bug 解释了为什么"规则层明明没分类错，模型也每次都能出正确计划，却总是失败"——因为**根本没走到模型**。

### 3.2 我做过一次"指标变好但语义变坏"的修复（诚实性加分项）

**现象**：搜索 0 结果。原因是 LLM 从简历派生出 `AI/LLM 算法工程师`，而站点是**字面子串匹配**，标题里只有 `AI算法工程师`、`NLP算法工程师`。

**我的第一版修复**：把这些复合词一律拍平成 `算法工程师` —— **命中数从 0 变成 299，看起来修好了**。

**问题**：它把 `AI/LLM`、`NLP`、`RAG` 四个**不同方向**塌缩成同一条查询，**静默丢掉了用户要的专业方向**。这比报错更危险。

**最终修法**：方向词做**独立 token** 匹配（标题或技能标签），只在站点确实没有该方向时才放宽。同时区分两类词：
- `RAG`/`LLM` 是**技术栈**（600/543 条岗位在技能标签里）→ 必须靠 JD 匹配；
- `Agent` 子串命中 11666 条但**独立 token 命中 0 条** → 全是"配送"里的字母巧合，必须挡。

**这条能讲出水平**：主动识别"指标改善掩盖了语义退化"，并用数据把两类词区分开。

### 3.3 为什么"不确定的结果永不重试"

投递点击后进程崩溃 → 简历**可能已发出**。重试 = **重复投递**，对用户是实质损害。

所以状态机必须区分：

| 情形 | 判定依据 | 处置 |
|---|---|---|
| 点击**前**失败 | `checkpoint='failed_before_submit'` | **可安全重试**（什么都没发出） |
| 点击**后**结果未知 | `submit_started` / `submission_unconfirmed` | **标为待人工核验，永不自动重试** |

这个区分是**代码里已有的**，`delivery/automation.py` 用 `submit_started` 分流。**这是整个项目最该讲的设计决策**，因为它体现了对"副作用不确定性"的理解。

| 8 | **给 `automation_decisions` 加保留策略** | 实测 **1 行/分钟 ≈ 1000 行/天 ≈ 40 万行/年**，无上限增长 |

## 6. 面试怎么组织这段经历（建议结构）

**不要按"功能列表"讲，按"问题 → 约束 → 决策 → 验证"讲。**

1. **问题**：求职者每天要筛几百个岗位，重复劳动。我做一个代替我执行的 Agent。
2. **关键约束**（这里是分水岭）：
   - 它要**代替我对外产生副作用**（投递）→ 必须解决授权与幂等；
   - 点击后结果可能未知 → 必须区分"可重试"与"必须人工核验"；
   - 进程会重启、用户会手动操作 → 状态必须持久化，且能感知外部变化。
3. **架构决策**：三层意图路由（规则不否决）、持久化 run/step 状态机、一次性授权 + 预览绑定、单浏览器会话串行化、观察式规则框架。
4. **量化**：分层评估通过率；搜索漏斗各环节数字。
5. **踩过的坑与修正**（最有价值的部分）：
   - 提取器拥有否决权 → 契约职责混淆；
   - "指标变好但语义变坏"的修复 → 主动识别并回退；
   - 一次临时浏览器错误导致无谓重新授权 → 用 checkpoint 证明"点击未发生"从而安全重试。
6. **边界与未做**：真实招聘网站禁止爬取，因此**只对本地模拟站执行写操作**；不绕过验证码；无自动化回归（并说明验证边界）。

**第 6 点的第一条特别重要**：主动声明"不爬真实站点、不绕过验证码"，把项目定位成**受控环境下的授权代理**，既合规又显得清楚边界——比试图回避这个问题好得多。

## 7. 一句话总结

**需求与实现已经闭环，并且有一次性完整成功的端到端证据；真正的短板不在功能，而在"可复现性"（缺依赖清单）与"可量化"（评估数字未更新、漏斗未测量）。**

补上这两块，这个项目就能从"我做了个 Agent"升级为"我解决了一个有约束的授权执行问题，并且用数字证明了它"。
