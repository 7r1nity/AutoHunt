# 意图识别与任务编排 Review

更新：2026-10-08。Review 基线：DeepSeek 修改提交 `425a1e2`。

## 发现的问题

1. **高影响：复合目标仍会遗漏。** `core/composite.py` 仅在搜索含具体约束、且附带投递/学习计划时命中；“帮我找工作，然后生成成长计划”及简历、查询、条件修改的组合没有统一入口。新增 guard 的方向正确，但不是完整编排。
2. **高影响：启动不等于完成。** 转到原生工具循环后，`job_search_start` 成功会立即返回，搜索后的目标仍可能丢失，也可能读取上一轮 JD。
3. **高影响：动作判断与参数完整性混在一起。** 小模型只有分类标签，没有完整参数；标签回退曾使用 1.0 置信度。控制指令正规化可能删除问号或引号。浏览器处理器异常后再转模型，有重复执行风险。
4. **中影响：语义契约重复。** `workflow/compound.py` 与新增 `core/composite.py` 各自判断复合请求，条件不同；后续添加场景容易分支漂移。

保留 DeepSeek 的 `.gitignore` 排除 `_diag/`；两个重复模块合并为通用规划与执行模块，没有覆盖它的其他历史提交。

## 当前实现

`规则完整解析 → 可选小模型分类提示 → 主模型无工具规划 → 代码校验 → 注册表执行 → 持久化步骤状态`

- 规则继续处理完整、单目标的高频搜索/条件修改/状态查询/详情/控制，不把未消费的整句充当岗位词。
- 小模型的置信度、边际及来源分别判断；无 logprobs、低置信、低边际或非法数值回退主模型。分类不是参数完整性或动作授权的证明。
- `workflow/planning.py` 从实际工具 schema 构建能力列表，登记全部目标、参数、原话、缺槽和依赖。数字、岗位词、城市、分数范围与长期偏好核对来源；明显遗漏目标时不执行半条命令。不确定薪资/分数需补充，不猜阈值。
- 待补请求保存原目标、回答、简历版本与独立有效期；自由表达的补充回答由模型判断是否继续原任务，不强制固定口令。撤销授权先持久化，即使模型失败也不能复活。有效期不清除简历偏好、会话搜索条件或历史。
- `workflow/execution.py` 执行最多 8 个步骤的依赖图。每步先持久化 claim，再调用唯一注册表；搜索后的结果、统计、成长计划、模拟投递绑定本次任务 ID。前置失败跳过依赖分支，独立分支可以继续。
- 简历修改产生提案，等待审批，不代表已写入；模拟投递只是有限入队，保留预览、一次性授权、明确回复后发送及结果核验；不开放真实网站投递。
- 序号审核由执行器绑定最新已展示快照；简历修改按解析后的稳定条目 ID 绑定目标，同名项目不会靠模型猜标题。“先查看、再修改/审核”的后一步不需要模型预测尚未创建的快照 ID。
- 已领取步骤崩溃/未知失败不重放；取消/新计划替代、简历变更、授权过期阻止后续写入。前端运行记录展示逐步状态与依赖，搜索摘要、成长计划与统计通过事件刷新。

## 验证与交付边界

本次使用临时内存/数据库和虚拟模型、浏览器诊断：复合目标覆盖、规则重搜、15 个/12k 条件继承、问句/引用/否定、分数范围、模糊薪资补充、依赖成环、搜索完成前禁止后续动作、同轮证据绑定、失败隔离、陈旧授权、claimed 重启恢复。未操作真实招聘网站，也未修改用户历史数据。

执行 Python 编译检查、前端 TypeScript 检查。按仓库约定没有新增测试文件；**没有持久自动化回归覆盖**。诊断只能证明这些输入下的状态、安全与协议行为，不能证明所有行业/自然语言的识别率。

另外使用已配置的 DeepSeek，仅发送虚构条件与公开工具结构做规划检查，没有发送真实简历/历史、没有执行工具。验证了“搜索＋分数投递＋成长计划”“无具体筛选的搜索＋成长计划”“条件修改＋重搜＋统计”“先读简历＋修改提案”四类请求；最后一类首次被过严的修改语义拦截，修正后重跑通过。一次检查耗时约 8–20 秒，仅是本次样例，不是延迟分位数或全面模型评测。

仍需后续评估：跨行业多轮真实模型样例的目标覆盖率、槽位准确率、必要澄清率、误授权率、规则命中率、模型调用次数及 P50/P95 延迟。当前通用执行器不支持任意代码、动态工具生成或无限重规划；开放式阅读回答的展示仍偏确定性，不是通用研究 Agent。旧原生工具循环与旧复合检查点仅保留兼容恢复，不作为新复杂请求的默认入口。
