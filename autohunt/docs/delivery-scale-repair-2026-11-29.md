# 单次100+搜索、投递与完整看板验收

日期：2026-11-29（北京时间）。修复基线为 `a7840ae`。前一轮[容量评估](delivery-scale-2026-11-29.md)保留为历史记录，不用修复后的成绩覆盖原来的100条限制和启动停顿。

## 改动

1. 搜索结果、分组总量、会话条件、工具schema、追问补参和稳定序号统一支持最多200个。新增目标超过旧候选预算且本次没有明确新预算时重算预算；明确指定更小候选预算仍可返回部分结果。候选读取预算最大200，不能保证筛选后一定凑足200个。
2. 看板新增带`total`和`snapshot`的分页接口。前端读取完整批次后才发布；任一页失败保留上次完整结果；页间变化返回409，最多整批重读一次。旧数组接口默认100条继续兼容，前端不再依靠它获取完整看板。
3. 后台HR观察的SQLite读写移至有界线程通道，观察状态、checkpoint与事件一次事务保存。重复观察及重启恢复不重复发事件；取消会等待已启动的写入结束，取消或已结束任务不能被旧观察复活。只读进度查询也从事件循环移出。
4. 同一计划的条件继承按依赖关系投影，先更新/清除条件再搜索时绑定更新后的参数；本步骤明确参数优先，独立分支不继承别的分支更新。不会在执行时悄悄替换已绑定的投递参数。
5. 修复真实后台循环在公平轮转后把“已有可执行HR回复”误当成空闲并等待30秒的问题。观察和执行共用绑定、回复及检查到期判定；可立即执行的工作使用短调度间隔，未回复、未到期、已停止、无有效绑定或结果未知的任务保留原等待与安全边界。
6. 后台观察采用状态版本条件更新。异步读取的旧`running`快照不能在执行器完成或切换岗位后覆盖新的回执；岗位阶段与投递执行记录在同一事务中处理，已确认提交不能因旧的失活判断被降为结果未知。

投递继续采用逐个浏览器动作、多个岗位同时等待HR回复。入队、已沟通、等待回复与已确认发送仍是不同状态；保留一次性授权、账号与主简历版本绑定、去重、人工验证接管和不确定结果保护。

## 端到端验证口径

`evaluation.delivery_scale_full_chain`使用新建的虚构账号和简历、独立SQLite及仓库内模拟站夹具。指令经实际API、Planner、Executor和工具注册表进入**真实网页搜索**，不预先往Agent岗位表或搜索回执表写120条结果。随后由生产`MockWorkflowCoordinator._loop`、规则和唤醒机制自主派发与监测，保留30秒轮询，不由测试逐次调用派发或回复检查方法。最后核对模拟站SQLite、Agent本地记录和前端卡片。

模型响应为脚本夹具，HR回复由测试角色通过隔离站点招聘方接口发送。因此这是工程全链路验收，不是真实模型语义准确率、真实招聘网站成功率或HR实际回复速度。

| 验证层 | 验证内容 |
| --- | --- |
| 单次100+ | 本轮140个新搜索结果，仅前120个进入投递队列、120次沟通、120条HR回复、120条真实模拟站申请记录、120张已投递卡片 |
| 范围与数量反例 | 先通过真实旧搜索保存1个高分岗位，另准备5个超额同关键词候选；旧岗未入队/沟通/投递且内容不变，超额候选不进入本轮结果；完整看板额外保留旧岗1张 |
| 20个示例指令 | 搜索40个、仅投递前20个；额外预置旧城市和高薪条件，验证明确清除后不会又继承旧范围 |
| 搜索边界 | 120/200、分组总量、201拒绝且无副作用、旧预算扩容、明确小预算、中文补参、第120/200个定位 |
| 队列 | 批次120/200、重叠请求去重、跨轮隔离、暂停/取消、重开数据库、简历变化保护 |
| 看板 | 实际鉴权API的250条三页、前端200张与250张卡片、末页故障与快照变化恢复；纯分页reader另测1250条 |
| 后台 | 120个真实观察协程、实际`runtime.start()`恢复、状态事件事务回滚、取消排空、重启去重与进度查询 |

前端除数量外还核对每张卡片对应的唯一岗位；本轮额外20个未选岗位及旧轮1个岗位保留在待审核，完整看板分别为41/141张。所有远端申请使用的简历内容与文档ID、版本、摘要均需与授权主简历一致。独立ASGI组装不启动整个生产lifespan，测试主动启动的是实际协调器循环；不能将其等同于真实网站或全量HTTP/SSE服务的长期压测。

量化结果、最终日志路径和测试结果见[机器汇总](../agent/evaluation/reports/delivery-scale-repair-20261129.json)。每次运行的原始JSON、逐阶段日志及隔离数据库在本地`agent/evaluation/results/`，这些运行数据不提交Git。

最终20次验收用时90.752秒，最终120次验收用时290.492秒；包含本地搜索、真实30秒回复轮询间隔、测试角色回复和展示核验，两轮重复沟通/投递均为0。其间分别执行45/145次脚本模型响应，外部模型请求均为0，不能将这些耗时作为真实模型或HR响应速度。

后台版本CAS与取消专项21/21、搜索边界及依赖投影28/28、队列13/13、分页API9/9、分页/compiled hook15/15通过；另有189项调度与控制回归、837项共享语义契约、20项引用链路及原UI回归通过。测试组存在功能重叠，不合并为“独立用户场景”的样本量。

## 后台性能的改善与限制

同一台机器、120个虚构等待记录的短时组件测量：

| 指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 集中启动阶段最大事件循环延迟 | 3090ms | 12ms |
| 稳态等待最大事件循环延迟 | 27ms | 27ms |
| 进度查询阶段最大事件循环延迟 | 589ms | 42ms |
| 进度查询阶段p95事件循环延迟 | 589ms | 27ms |
| `runtime.start()`返回 | 未测 | 31.405ms |
| 恢复后120个观察器均完成首轮观察 | 未测 | 535.319ms |

改善的是事件循环响应能力。进度查询本身p50从约548ms增至1010ms，前台请求入队p95从26ms增至39ms；不能声称所有操作更快。各阶段窗口短、负载有限，也未测HTTP/SSE长连接压力，不能把这些数字写成生产SLO。

## 复跑

从`autohunt/agent`使用项目虚拟环境运行；浏览器验收需要Playwright Chromium和已启动的本地AutoHunt前端。评测浏览器拦截全部业务API，不操作当前用户的会话或招聘网站。无需填写模型密钥。

```powershell
.\.venv\Scripts\python.exe -m evaluation.search_scale_boundary_contract
.\.venv\Scripts\python.exe -m evaluation.delivery_scale_contract
.\.venv\Scripts\python.exe -m evaluation.runtime_io_contract
.\.venv\Scripts\python.exe -m evaluation.delivery_scale_runtime --count 120
.\.venv\Scripts\python.exe -m evaluation.job_board_pagination_contract
node evaluation/frontend_pagination_contract.cjs
.\.venv\Scripts\python.exe -m evaluation.delivery_scale_surface --jobs 200
.\.venv\Scripts\python.exe -m evaluation.delivery_scale_full_chain --count 20
.\.venv\Scripts\python.exe -m evaluation.delivery_scale_full_chain --count 120
```

`--count 200`也可运行完整隔离链路，但本次完整浏览器验收只报告实际执行过的20和120；200只报告入口/配额/队列边界与看板展示。结果不足时报告缺额，不补入其他轮次、不扩大筛选条件，也不凭“入队”认定已经投递。

## 示例指令

> 在模拟招聘网站新搜索40个当前简历方向的岗位，清除旧筛选条件、不限城市薪资和分数，对本轮结果自动投递前20个，已沟通或已投递的跳过，先沟通，收到HR回复并确认可发送后自动发送当前主简历，不足20个则处理现有岗位并报告缺额。

需要已上传并启用主简历；登录或验证码时完成人工接管。招聘方尚未回复时保持后台监测，不能保证立即得到20条已发送回执。
