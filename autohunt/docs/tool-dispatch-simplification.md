# 工具执行简化（2026-10-11）

## 当前分工

用户输入和有效上下文 → 规则/可选小模型路由 → 模型解释参数和依赖 → schema/DAG 校验 → 持久执行器 → 工具模块。

删除的是通用工具注册表中的第二次授权核对，不是删除实际投递保护。

- 注册表只检查工具是否存在、参数结构、每轮8次预算及相同调用重复；不读取旧计划/摘要/哈希来决定是否允许搜索或成长计划。
- 执行器持久化 claim、检查取消/撤回与任务归属、绑定简历证据、控制依赖、超时和恢复；通用计划30分钟期限不再阻止执行。确认问题的有效期与投递令牌自己的有效期不变。
- 投递规划只在范围未明确时询问；注册表内的投递执行器要求已确认范围。投递模块保留逐职位预览、一次性令牌、账号/职位/简历绑定、验证码接管和不确定结果不重放。真实站提交禁用。
- `action_authority` 是为存储兼容保留的字段名，当前只携带步骤、结果来源和投递范围元数据。`authority_binding` 是旧审计字段，不再由工具注册表核对；实际投递令牌是不同的机制。
- 原 `AUTOHUNT_APPROVAL_POLICY/THRESHOLD` 不再控制通用工具执行。风险分级辅助类型保留用于旧接口/评测，不是当前调用门槛。

## 新计划与任务接续

前台启用计划时，`persist(..., activate=True)` 通过一个 `instruction` 状态操作同时更新完整执行摘要和 `tasks.plan_id`，数据库以同一个读改写事务保存。不能再出现执行指针是新计划、会话记录仍是旧澄清计划的半更新状态。不同计划的旧后台保存只能更新自己的执行日志，不替换当前会话指针。

继续失败/暂停任务仍先读取持久执行记录；沿用原逻辑任务，保留完成结果与未执行分支，只恢复明确未产生副作用的断点。用户新增条件使用现有计划修订入口更新未执行步骤，不能重放已沟通/已投递步骤，也不能用上下文猜测发送是否成功。

缺简历的澄清请求尚无已执行步骤；上传使简历版本改变后可以产生新版执行计划，但启用必须明确、一致地替换旧澄清记录。不能把前台替换误当作后台覆盖。

## 测试与已知限制

所有运行使用脚本模型、合成请求和临时数据库，没有向模型发送真实简历，也没有打开招聘网站或发送申请。

| 契约 | 最终结果 |
| --- | --- |
| 动作派发（含上传后的完整状态切换、SQLite重新打开、异步依赖） | 20/20 |
| 恢复、停止、检查点、HR监测状态 | 692/692 |
| 薪资条件与计划修订 | 16/16 |
| 内部状态保真与出口脱敏 | 14/14 |
| 搜索报告发布 | 14/14 |
| 投递预览/令牌/简历绑定与循环控制 | 17/17 |

修复前两条新增状态/期限回归失败，移除重复门槛并原子激活后通过。恢复复跑曾发现未确认投递被测试替身绕过，修正任务恢复的投递范围检查后通过；失败日志保留。

可复跑：在 `autohunt/agent` 使用 `.venv/Scripts/python.exe -m evaluation.action_contract`；其他契约模块为 `recovery_contract`、`salary_revision_contract`、`privacy_contract`、`reporting_contract`，以及 `evaluation.run --kinds delivery_contract runtime_contract`。

旧语义基准838例的修改前隔离基线为357通过/481错误，修改后为817通过/21错误，剩余失败ID均在基线失败中。旧脚本草稿缺少范围确认字段、旧路由替身缺属性、部分旧规则/规划预期等仍未收敛。该对比同时调整了旧评测使用的注册表接口，不能当成真实用户请求的准确率提升；不把这21例计入已通过契约。

日志目录为 `agent/test-results/`；修改前源代码副本及基线日志在本地 `.runlogs/dispatch-baseline-*`，不提交运行记录。上述结果不是完整浏览器E2E、真实模型质量或所有多轮场景都可用的证明。
