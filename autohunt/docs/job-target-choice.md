# 点击确认岗位与互补移除

## 本次故障

本地执行日志和数据库核对表明：移除工具已经软移除了5个非目标公司岗位，保留全部历史；问题不是没有调用移除工具，而是规划器把“其他”缩成“该公司以外”，留下该公司全部候选。用户选择一个候选后只接续了投递，没有再按最终选中对象计算其余岗位。

定位输入原先缺少匹配分；模型也可能把“82分的公司岗位”变成公司名称加最低分门槛，丢失精确定位条件。移除排在投递之前，歧义又在投递阶段才暴露。这是对象绑定与依赖顺序问题，不是缺少移除工具。

## 接口和依赖

采用可复用的目标锚点，不新增公司名/分数例句白名单：

```
job_target_resolve(selector完整描述, scope=board)
    ├─ 需要选择 → 持久候选卡 → 用户点击具体ID
    └─ 已定位 → job_remove_selection(exclude_target_step_id=定位步骤ID)
                     └─ mock_delivery_start(target_step_id=同一定位步骤ID)
```

定位是只读步骤，结果包含选中ID、岗位事实指纹和冻结范围。移除计算“范围ID减去选中ID”，即使其他岗位属于同一公司也会纳入。初始规划和修订共用 `workflow/target_selection.py` 加依赖并验证引用，完成定位前不允许领取关联写动作。它是对象关系，不是另一次关键词匹配。

候选卡通过 `POST /api/v1/runs/{run_id}/target-choice` 提交会话、choice_id、step_id、expected_revision、job_ids。前端不提交自然语言“第二个”，也不提交自己提供的岗位事实或授权记录。后端在会话锁和版本CAS下核对持久候选，完成定位步骤后安排原运行的watcher；该HTTP接口本身不移除或投递。旧单岗位投递/移除步骤的候选可点击回答，以同快照序号绑定后接续，避免重新模型理解。

重复提交同一次同一选择返回原回执；不同二次选择、外会话、过期版本、候选变化、简历变化或已取消任务不会产生副作用。暂停任务只保存选择，不启动后续步骤。看板范围有变化时追问，不静默扩大删除范围；超过200个看板对象要求缩小范围，不截断后声称移除全部。

## UI

frontend-design用于沿用页面现有令牌、字体和可访问的选择卡，提供手机布局、键盘焦点、处理中禁用和就近状态反馈；codebase-design用于把目标绑定/互补计算集中到共享模块，规划、修订和执行不各自重做自然语言解释。卡片显示公司、岗位、城市、薪资、匹配分。重复候选的文字追问缩为一次简短提示；文字回答仍兼容。
