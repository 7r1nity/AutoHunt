# 规划输入的工具定义去重

## 问题与实现

2026-11-27 的一次请求在调用主模型之前超出应用的 48,000 输入估算上限。完整输入估算为 54,892，会话状态仅约 848。静态工具定义是主要来源，而不是搜索或投递数量。

原实现把全部工具的参数结构直接放入规划请求。搜索与更新条件同时包含全局筛选和分组筛选，投递再次包含相同筛选；一份筛选结构又展开六层。默认启用的完整能力配置即使使用空会话也估算为 53,662。

`agent/app/llm/schema_catalog.py` 将重复的 JSON Schema 节点保存在规划目录的 `$defs`，工具参数通过本地 `$ref` 引用。`capabilities` 是独立目录文档，结构为 `{"$defs": {...}, "tools": [...]}`；引用从该目录根解析。定义名是目录内的确定性短编号，不是授权 ID 或完整性摘要。

- 所有原有可规划工具仍在目录中；新增注册工具自动进入，不增加一套按用户词语筛选的工具白名单。
- 只共享相同结构，展开后与原工具参数逐项一致，保留字段说明、类型、必填项、枚举、组合规则、薪资单位、上下限、空值语义和树深度限制。
- 只处理 JSON Schema 位置，不把 `default`、`enum`、示例中的业务对象改成引用。
- 已含 `$ref`、`$id` 或定义作用域的参数结构保持原样，避免移动后改变原引用目标。
- 规划提示明确公共引用含义，模型仍输出实际参数，不输出引用；规划 JSON 使用紧凑序列化。
- 执行端的 `registry.schemas()`、参数校验、授权、队列和发送保护继续使用原结构。没有提高预算上限、截断用户条件或删除工具能力。

本次仅改变 `plan_request` 的模型输入副本。原生工具循环的供应商 tool schema 路径没有修改，不能把此结果解释为所有模型调用的输入缩减。

## 观测与测量

运行事件 `planning_catalog` 记录工具数、共享定义数、目录优化前后的估算体积；不新增 prompt 正文或个人数据日志。既有 `context_budget` 继续记录包括系统说明、完整当前请求及输出余量的最终输入估算。目录体积与最终输入体积的统计范围不同，不应直接相加。

在同一估算器、28 个可规划工具、空会话/条件、固定虚构请求与默认预算下，规划输入封装从 **53,662 降至 21,439，减少约 60.0%**。专项中实际经过 `LLMManager.generate` 传输边界的合成请求估算为 22,181；含 15,784 会话状态的合成请求估算为 37,312，均低于 48,000。这些是应用的 ASCII/3 + 非 ASCII×2 估算，不是供应商 tokenizer、账单 token、延迟或准确率测量。实际体积随工具配置和会话状态变化。

真实必要状态依然受预算保护；超过剩余输入空间时保留原记录并拒绝这次模型传输，不静默删条件或自动重放副作用。

## 后续：条件结构错误与用户信息缺失分开

同日新记录显示主模型已正确生成城市、非外包和月薪区间，但薪资叶只给了完整 `salary` 而漏掉重复的 `text`。旧运行时拒绝该叶，三次格式修复仅收到泛化错误并重复同一结构，最终把内部缺陷展示成“请补充filters”。这与之前的静态输入超预算是两个问题。

完整结构化薪资现在可以省略或留空说明；程序仅从已验证的 `SalaryPredicate` 生成显示文本，不解析用户原话、不补金额或单位。非薪资语义叶仍要求有效文本。公开参数结构和运行时使用相同的条件分支契约，原有说明与用户引用保持原值。

其他树形结构错误通过 `technical_issues` 记录字段、嵌套路径、错误类型与原因；模型反馈不复制异常的 `input/ctx`。最多三次修复和整体规划时限继续生效。耗尽后保留原条件，相关步骤以 `predicate_repair_exhausted` 结束，聊天明确说明系统解析失败；业务上缺少城市等信息仍是用户追问。独立且结构完整的范围分支仍需范围复核，不能因另一步格式错误而跳过。

普通“继续”不能把隔离后的 `filters=None` 直接恢复执行。用户显式补正未执行失败步骤时，需提供完整替换条件，重新通过校验与范围流程后才可恢复；原始失败与条件进入尝试历史。已有发送、撤回和结果不确定的步骤继续受原保护约束。

专项入口为 `evaluation.typed_filter_contract`、`evaluation.predicate_repair_contract` 与 `evaluation.predicate_revision_contract`。合成条件覆盖完整薪资叶、布尔组合、具体错误反馈、修复耗尽、真实业务追问、失败后显式补正、普通继续保护，以及规划到聊天结果的隔离链路。仍不代表真实模型的理解准确率，也不发起招聘操作。

修复后验证：三项新专项分别 15、20、14 项，共 49 项；完整工程回归按既有收集器分为三个互不重复的模块组，共 39 个模块、958 项通过，0 失败、0 错误。三组源文件哈希一致且测试期间未变化，外部模型和招聘操作均为 0。汇总位于本地 `agent/evaluation/results/predicate-full-regression/20261127T090943.872840Z/summary.json`，各模块日志与首次失败路径保存在汇总引用中。

首次回归保留了一个过时的“格式修复耗尽等待用户输入”断言，以及一个新增反馈逻辑的异步异常缺陷：校验协程抛错后，反馈代码误把协程当成已验证字典。已更新产品契约断言，并修正赋值时机、增加异步拒绝后成功与有界耗尽两项回归。最终成绩只统计修复后的 958 项，不把重复执行或首次失败累加为额外样本。
