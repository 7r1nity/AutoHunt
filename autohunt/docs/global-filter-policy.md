# 全局删除筛选维度

2026-11-28，按用户要求将以下维度从筛选链路统一移除：

- 外包、第三方、劳务派遣等雇佣关系。
- 实习、正式、全职等岗位性质。
- 应届、校招、社招等招聘对象或渠道。
- 工作、行业和项目经历的年限限制。

此策略适用于当前指令、旧会话、保存偏好、搜索参数、分组配额、看板准入及投递范围，不再区分“默认门槛”和“用户曾明确提出”。本版本没有按会话恢复这些条件的开关。薪资金额/单位、城市、数量、分数、公司身份、福利、学历和技术能力等其他条件继续保留。默认 JD 资格诊断仍仅供参考。

原始简历、JD、历史对话和执行回执不删除。职位名称或公司名中的原文仍用于身份定位；例如“第3个实习工程师”保持第3个对象，不改成全部岗位。数据中出现这些词不等于它们仍参与筛选。

## 统一入口

共享实现位于 `agent/app/core/filter_policy.py`，版本标记为 `retired-screening-dimensions-v1`：

- `project_filter` 清理条件树。保留剩余 AND/OR/NOT 的结构，清理删除后为空的组合；全部被移除时不设置语义筛选。
- `project_keywords` 清理排除关键词与岗位关键词中的禁用限定，保留角色、技能和公司身份。
- `project_groups` 去掉类别限制并保留请求总数。例如“5个正式、5个实习”保留总数10；“深圳5个、实习3个”变成深圳配额5个及不限类别配额3个，城市组优先占用符合者，开放组不抢占其名额。
- `project_arguments` 供规划、动态修订、会话状态与工具网关共用。模型输出和旧参数都必须经过相同处理；授权前保存有效参数并重算绑定，执行端再次检查。

结构化薪资保留金额、上下界和日/月薪单位；旧 `applies_to=internship` 不再依赖岗位性质来判断适用性。月薪和日薪不互相猜测或折算。混合薪资叶中的保留条件独立保存，不能因删除“正式/实习”而丢掉深圳、住房补贴或技能要求。

常见旧文本由集中词义投影兼容，并支持可选 `dimension` 标记。第三方库、第三方支付、正式上线经验、人力资源专员和完整公司身份不作为雇佣关系条件误删。无法无损处理的复杂条件句保留原文进入模型内部修复，不静默丢弃薪资等约束，也不在读取旧状态时直接终止新请求。

## 执行和旧状态

`runtime/filter_policy_migration.py` 在启动时持久化清理旧搜索条件、有效会话范围、保存偏好与未开始步骤。变更的未执行动作重新绑定参数，旧审批失效，计划安全暂停；用户明确继续即可按剩余条件接续，不要求补回已禁用条件。已完成、执行中、未知副作用与 HR 等待步骤不重放。

`runtime/filter_policy_results.py` 重新核对当前会话、当前简历、已完成搜索中的已有候选：

1. 检查源回执完整性、原始 JD 指纹和简历版本。
2. 仅复用有原文依据的保留条件判断，并使用确定性薪资核验；启动迁移不调用外部模型。
3. 保留条件仍未知的岗位继续待核实，不把“删掉一个条件”当成其他条件通过的证据。
4. 原子保存新筛选回执和看板准入，保留本轮原评分及已完成投递记录；清除失效的应用生成“禁止自动投递”提示。
5. 在聊天保存迁移结果和更新后的简表。旧序号尽量保持原顺序，新岗位追加；后续引用绑定新展示快照。重复启动不重复消息或重置当前焦点。

迁移不启动新搜索、不创建投递授权、不新增沟通或简历提交。已有授权队列和 HR 等待监测继续使用其冻结记录，原始事实变化、简历绑定、用户停止、重复发送与未知提交结果保护继续生效。

纯禁用属性的目标引用不会变成全选删除：“移除实习岗位”在该维度已禁用时为零操作并说明原因；先定位后删除的链式引用同样不能扩大为全看板。有效的职位序号、名称和公司身份仍可正常操作。
