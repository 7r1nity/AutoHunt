# 2026-10-26：评测暴露的系统问题修复与复验

本轮落实[根因报告](benchmark-root-causes-2026-10-26.md)的五项修复，并修复真实复验新发现的计划版本绑定错误。代码修改、旧输出回放、真实模型和浏览器结果分别记录，不能相互替代。[机器汇总](../agent/evaluation/reports/systemic-repair-20261026.json)仅保留合成评测的统计，不发布原始运行数据。

## 实现与闭环

### 1. 条件 Schema 与运行时共用结构契约

`app/core/job_filters.py` 的 `NODE_CHILDREN` / `node_branches` 同时生成工具公开 Schema 和 Pydantic 结构约束：叶节点不能有子节点，all/any 必须有子节点，not 只能有一个。组合说明采用 label；兼容旧模型在组合 text 中输出说明的情况，将其迁移为 label，保留真实子树，不删除条件。

薪资谓词的数值边界及面议规则也进入公开 Schema。工具网关支持 anyOf/oneOf/const、数字类型及带索引的错误路径。规划中的可修复谓词问题仍进入有预算的模型修复/局部追问；不会因公开 Schema 与运行时矛盾反复修复。未修改的旧条件序列化保持兼容，条件策略版本升为 3，使新判断不复用旧策略缓存。

### 2. 条件理解增加独立、只读的范围复核

`app/workflow/scope_review.py` 只复核新增或变化的 filters、result_groups、salary_min、min_score、max_score。规划器仍负责工具、参数和依赖；复核器不能改工具、目标、城市、数量、依赖或授权字段。明确的条件误解可修正后重新经过同一编译/动作绑定；确有歧义或复核不可用时，只让受影响分支等待补充，保留其它独立分支。

复核输入限于当前请求、原任务、结构化条件及候选范围，不包含简历或 JD。薪资边界附近的示例由确定性算术生成，帮助模型发现“最低15K”被误写为区间有交集即可的情况。数值最低薪资默认核对岗位区间下限，面议只有用户明确允许时才加入。沿用旧条件且只改城市/数量的修订不重复复核；待复核分支重试则再次核对，不能沿用失败结论。

新增/变更范围可能增加一次只读模型调用，受剩余总规划时限和最多18秒的局部时限约束。复核不是新的执行授权，也不能证明模型绝不误解；这仍需独立语义评估。

### 3. 岗位目标共用引用与稳定快照

`app/runtime/job_references.py` 提供 ordinal、snapshot_id、title、company、location 的结构化引用，兼容旧字符串。详情、移除和投递共用 `resolve_job_targets`：先由快照序号锁定身份，再核对职位/公司/地点，不把“职位名+公司名”作为单一字段匹配。

组合描述的语义 fallback 只能核对已锁定岗位，不能换另一个岗位。越界、快照冲突、模型序号与用户明确序号不符、内容指纹变化继续要求核对。只读详情同样保留内容完整性检查，没有绕过岗位指纹。

### 4. 投递观察与副作用阶段

`app/delivery/mock_site_adapter.py` 在固定控件失效时，可使用已绑定简历区域内唯一、语义明确的发送控件；不会使用全页普通“发送”按钮。观察区分等待 HR、验证、缺控件、可发送和已发送。

在真正点击前的 callback 才记录发送尝试，预检失败不再提前标为“可能发送”。点击后的未知结果仍只读核验，不盲重放。针对模拟环境的显式新增确认步骤，最多前进一步；任何申请 POST 或不确定点击后禁止再次发送。缺少用户尚未提供的必填信息则等待人工，不编造答案。

账号/岗位/简历绑定、一次性授权、HR 回复门槛和真实网站禁止自动提交均保留。本轮未修改本地招聘网站的业务逻辑。

### 5. 匹配器获得最小化、可溯源的候选人事实

`app/jobs/candidate_facts.py` 只输出用户已批准的数据范围：来自简历的学历/年限短引用（每类最多200字符）和最多4条已确认项目/课程/代码证据（各最多700字符），先脱敏，再发送给匹配模型。完整简历、联系方式不作为新增匹配输入外发。原文仅在本地用于核对引用来源。

模型分别返回相关性分数和硬条件 pass/fail/unknown；JD 引用与候选证据必须能在输入原文中核对，无法核对降为 unknown。高分不能覆盖已知学历/年限不满足。新记录的资历未知不会进入批量自动投递；明确指定岗位仍沿用既有未知条件处理，已知不满足仍排除。旧的无资历元数据记录不被本次迁移自动撤销授权。

资历证据绑定简历指纹并持久化；部分 upsert 未提供该字段时保留旧值，显式更新才替换。旧候选画像没有带来源的学历/年限事实时保持未知，需要重新解析后才能补齐，不能从技能名猜测资历。

### 6. 真实复验新发现：计划版本由应用绑定

首轮40次修复后验证中，模型把 dialogue.revision 误填为计划 expected_revision，六组修订连续触发版本校验，另外两组预算耗尽，四个资历样本没能执行。该失败原样保存，不能算成功。

现在 plan_id / expected_revision 从模型可填写 Schema 移除，由应用在推理前读取计划快照并绑定。模型只描述业务改动。推理后若存储中的计划确实被其它请求改动，仍报告真实并发冲突，数据库 CAS 继续生效。模型填错机械版本不再误拒绝；并发写入也不会被无条件覆盖。

浏览器独立 SQL 审计确认：Agent 28条正确申请记录，0重复记录、0重复申请 POST、0条 HR 回复之前发送的简历，原通过结论未被更严格核验推翻。Agent 单次受控执行 p50约2.92秒、p95约5.08秒；不包含实时模型规划耗时。不是生产并发容量或真实网站成绩。

新增专项已接入跨模块回归入口；最终合并运行735项全部通过，0失败/错误，运行期间源码未变化。完整回归日志、各次失败与机器统计以机器汇总引用的本地路径为准，不能把重复跑过的契约数相加当独立场景数。

## 复现入口

在 `autohunt/agent` 中运行：

```powershell
.venv/Scripts/python.exe -m evaluation.context_ledger_regression
.venv/Scripts/python.exe -m unittest evaluation.systemic_repair_contract
```

已有合成原始模型输出在本地时，可零API回放；公开仓库不携带这些日志或本地模拟站：

```powershell
.venv/Scripts/python.exe -m evaluation.benchmark.frozen_replay --source evaluation/results/task-benchmark/session-20261026-v1 --output evaluation/results/systemic-repair/NEW-REPLAY --phase planning
```

真实模型 runner 为 `evaluation.benchmark.postfix_validation`，支持指定 case 和物理上限。任何新运行仍需用户明确同意目的地、数据和预算；CLI 开关不替代许可，不能通过新建输出目录重置预算。

## 仍需保留的边界

- 本轮未重做450对完整排序评测，4个硬条件样本不能证明跨行业排序质量提升；原数据仍是合成 oracle，不是人工 Gold。
- 实时模型只复测4组两轮场景，不是20组全量新模型复测；浏览器采用冻结规划，不是新的实时模型端到端成功率。
- 范围复核仍可能误判，并增加模型延迟/成本；本轮没有测量生产总体费用或证明任意自然语言零误解。
- 浏览器恢复是模拟站已知接口内的有限适配，不是任意页面改版自愈。未知副作用继续待核验。
- 没有对用户现有队列、聊天或简历执行测试，没有启动真实招聘搜索或投递；服务是否加载此提交需要通过实际部署确认。
