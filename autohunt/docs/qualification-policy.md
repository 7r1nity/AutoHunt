# 默认资历建议与用户筛选条件

2026-11-28 起，默认 JD 资历判断为参考信息。随后按用户追加要求，将外包关系、岗位性质、招聘渠道及工作/项目年限从筛选链路全局移除，即使旧指令曾明确要求也不再使用，详见[当前全局策略](global-filter-policy.md)。其余用户筛选条件继续生效。

## 此前为什么会被阻止

`app/browser/screening.py` 的匹配提示词原先包含：

> 额外输出requirements数组，逐项核对JD明确要求的学历、年限、资格等硬条件；无此类硬条件时返回[]。

模型逐项返回 `pass/fail/unknown`，以及 JD 原文和候选人证据。`app/jobs/candidate_facts.py` 检查引用是否真实存在于输入：无法核对的引用变成 `unknown`，没有证据不能猜成满足或不满足。

此前程序将任一 `fail/unknown` 聚合为资历未通过，把模型的 `APPLY` 降为 `REVIEW`；自动投递队列进一步排除这些岗位，数量批次也排除缺少旧版资历记录的岗位。因此，“搜索筛选通过”仍可能在投递时因模型推断出的另一套资格门槛未能入队。该问题属于匹配与业务准入策略，不是动作授权拒绝。

## 当前判断标准

| 信息 | 默认用途 | 用户明确提出时 |
| --- | --- | --- |
| 外包、第三方或劳务派遣关系 | 原文描述 | 全局移除，不作为筛选 |
| 实习、正式岗位 | 原文描述 | 全局移除类别配额，保留总数量 |
| 应届、校招、招聘对象 | 原文描述 | 全局移除，不作为筛选 |
| 工作或项目年限 | 原文描述、参考 | 全局移除年限限制，保留实际技能 |
| 学历、项目能力和案例 | 可选差异提示、面试准备 | 非禁用维度的明确条件仍保留 |
| 用户设置的薪资、地点、分数门槛及其他条件 | 用户范围的一部分 | 必须满足；证据未知不能假装满足 |
| 简历与账号绑定、重复发送、未知提交结果 | 执行保护 | 沿用现有核验与人工接管 |

匹配器仍输出相关性分数、匹配/缺少技能和理由。提示词的评分指引是搜索方向50%、技能证据30%、目标岗位10%、JD完整度10%；80分以上建议 `APPLY`，50–79分建议 `REVIEW`，低于50分建议 `SKIP`。这是模型评分指引，程序不会按这四项重新加权模型分数；模型异常或偏离当前搜索方向判断时使用已有规则回退。投递数量与用户明确设置的最低分独立执行，不能把默认建议阈值当成用户设置的自动投递门槛。

当前提示词明确说明：资格核对为可选参考，不得把 JD 中的学历、应届、年限或用工身份自动变成拒绝或待审核的硬门槛。规划提示词与工具说明另加入统一全局策略，禁止当前指令和旧历史恢复已经退休的四类筛选维度。

兼容模型仍返回的 `requirements`，继续核对原文并保留真实 `fail/unknown`，同时标记 `policy=advisory`；不改成虚假的 `pass`，不再因此修改分数、建议或排除投递。旧资历记录也不再成为默认门槛。简历摘要和原始证据继续保留用于版本绑定、回放与面试准备，历史数据不批量改写。

自动投递仍检查用户明确条件、分数、来源、当前简历、账号、停止请求、去重及外部提交回执。用户条件失败或未知、JD事实变化与简历变化不能因放宽资历建议而被绕过。

缺少简历版本绑定的历史搜索回执仍需核对来源；不会因为取消默认资历门槛，就把没有版本依据的旧记录改成有效投递授权。

## 验证

`evaluation.qualification_advisory_contract` 验证匹配提示与兼容诊断，`delivery_limit_contract` 和 `delivery_request_contract` 验证真实队列及用户指令到聊天链路；旧 `systemic_repair_contract` 的资格门槛断言按新用户策略更新，证据引用、简历版本及用户筛选保护继续检查。均使用合成数据与隔离存储，不调用真实模型或执行招聘操作。

历史排序和资历分类评测仍对应当时提示词与准入策略，不能直接当作新策略的效果结果。现有报告保留原值；新策略的真实模型排名质量需要另外获得外发范围与请求预算后测量。
