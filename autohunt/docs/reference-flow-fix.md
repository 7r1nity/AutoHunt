# 序号与混合动作的执行闭环修复

## 已确认的原因

原始规划正确识别了移除、投递、链接三个目标，却给详情工具传了裸数字字符串。工具内部坚持“第几个”格式，把合法序号当作数据库ID风险拒绝。前台已经报告该失败，后台收尾又报告一次：旧去重只记录完成步骤，没有记录已经告知的失败。

隔离重放还发现第三条链路问题：成功的详情查询在回答整理不可用时会被备用回复丢弃。真实模型评估另发现两个接口组合缺陷：已绑定定位步骤的投递被旧序号分支误挡；对象在前、明确只读的表达丢失了序号。这些都纳入修复，而非只添加某家公司例句。

## 共享引用与回复发布

- `runtime/job_references.py` 是结构引用模块的共享实现：序号、明确ID、可核对的名称限定和完全消费的单分支引用。它不提取搜索关键词、不决定是否授权，不扫描整条复杂请求猜动作。
- `resolve_reference(kind=job)` 将裸序号归一化；明确ID才按数据库ID在当前快照定位。序号加名称必须同时一致；移除不会重排原简表。名称/序号真正冲突、越界或快照不可用属于输入等待，不伪报不确定写入。
- 详情、移除、投递沿用同一已展示快照。执行器提供单步骤命令时，可恢复模型遗漏的明确序号；没有可识别完整分支时使用结构化参数，不按正则强行提取整个用户任务。
- `job_target_resolve` 的可信目标回执优先于旧裸序号保护；同计划、依赖和岗位证据核对仍保留。
- `step_receipt` 绑定步骤、execution_id、状态、参数和结果；前台已发布与后台待发布据此区分。内容相同的新尝试仍保留。旧日志必须有对应历史步骤才能回补回执，不能按工具名字猜已经说过。
- job_detail_read的最终链接/详情由已读取结果渲染；整理模型遗漏时补上，格式/服务失败时备用通道也保留。只作为其他步骤证据的查询按依赖图隐藏，避免重新出现无关职位列表。

codebase-design技能使三种调用共用一个结构引用接口，而不是新增三套序号/ID判断。语义描述仍归模型，外部投递、简历绑定与结果不确定保护没有取消。

## 真实模型与最终状态评估

仅发送合成指令、虚构岗位列表/状态和工具结构。读取已配置模型和加密凭据，但不读取用户简历、聊天、职位库；没有招聘浏览器。工具执行使用真实registry、DAG和临时SQLite；队列适配器只把合成对象入临时队列，不能沟通或发送简历。

总物理调用10次（含所有请求，没有供应商传输重试）：

| 阶段 | 场景/请求 | 结果 |
|---|---:|---|
| 首批真实模型 | 8条不同表达，8次请求 | 6通过、2失败，原始失败保留 |
| 修复后真实复测 | 2条失败表达，2次请求 | 2通过 |
| 最终代码离线重放 | 首批8条原始输入与响应，0新请求 | 8全部通过 |

首批失败具体是“定位回执后投递仍触发旧检查”和“对象在前只读链接的引用丢失”。没有宣称10次全部一次成功，也没有宣称8条是大规模语义泛化证据。重放必须恢复原始合成快照ID；用新随机ID会导致假的快照过期失败，评测入口已修正此夹具问题。另有分数与第三方被新序号语法误判的回归，已修复并记录失败日志。

观察的最终状态包括：移除集合精确、指定入队集合精确、链接对应正确岗位、链接实际出现在最终回复、零重复入队、否定投递无入队、冲突输入无写入、前后台不重复回复。它不是HR回复/简历上传的浏览器端到端验证，也未使用真实回答整理模型；链接保留另有脚本模型与生产整理模块契约验证。
