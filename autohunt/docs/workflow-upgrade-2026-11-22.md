# 多轮范围、沟通话术与面试准备

本次改动沿用现有规则 → 小模型 → 主模型路由及 Plan-and-Execute。重点是让不同操作共享明确的范围与证据契约，并打通新功能的执行、保存和查看入口。

## 三种范围

| 用户要求 | 修改的数据 | 对已有操作的影响 |
| --- | --- | --- |
| “搜索范围加上上海，其他不变” | 会话搜索条件、相应未执行搜索步骤 | 新一轮搜索使用新条件；不会将新增岗位自动加入旧投递队列 |
| “搜索不变，把投递门槛从85降到80” | 本批投递参数 | 保留未修改的城市、薪资、岗位条件；扩大范围进入确认，搜索条件不变 |
| “第6个虽然不符合原条件，这个也投” | 一个明确岗位的例外动作 | 确认仅对本次岗位、简历和动作有效；不清空其他岗位的筛选条件 |

`mock_delivery_start.scope_mode` 的契约：

- `inherit`：补投，旧条件和新条件取交集，分数不降低；提供 `selector` 也必须继承。
- `update`：显式字段替换、未提供字段继承；可以降低门槛或修改 OR 分支，扩大范围需要确认。
- `new`：独立批次的完整范围。
- 指定岗位且省略 `scope_mode`：独立选择，不搬用旧批量门槛；当前岗位的已知不满足条件仍不能被静默忽略。

应用在授权之前物化完整参数，并将结果冻结为 `new`，防止后续对话的范围指针改变已经审批的动作。`scope_mode` 只是参数继承方式，不能充当授权。

`allow_outside_search=true` 需要一个明确岗位及一次人工确认，不允许作为批量放宽开关。未知发送结果、错误账号、简历变化、已移除岗位和真实网站提交不属于这种业务例外。

## 每轮证据与后续步骤

新增投递队列的 `eligibility_json` / `eligibility_digest` 保存当时的分数、筛选依据、来源、会话、简历与原始岗位事实指纹。新搜索可以更新全局匹配缓存，但不会因此把原投递改成失败或用新分数取代已批准分数。实际 JD、原始标签、链接或简历变化仍会失效。

搜索结果及重新筛选回执新增 `analysis_receipt`，保存对应轮次的判断和简历版本。成长计划、结果总结和批量投递按已绑定的搜索回执读取；不能从最新全局缓存反向补出旧任务没有保存过的简历证据。旧记录缺少足够证据时保守提示重新核对，不自动伪造或恢复发送。

看板成员资格使用持久化的 `board_visible` 和 `removed_at`，不由另一次搜索的全局筛选缓存隐式改变。未核实通过的新候选仍不加入看板；用户指定重新筛选原轮结果或移除岗位时，成员资格按该操作更新。

显式绑定旧搜索回执的投递/分析，可以与新增搜索独立推进。模型虚构的任务 ID 不能据此绕过新搜索依赖。后台审批续接从当前运行的持久化计划读取已解析的岗位目标，不依赖会话后来指向哪一份计划。

搜索步骤仍自动带一份完成报告。投递入队、HR 等待和简历发送完成分别记录，成长计划读取指定分数/薪资范围的有效 JD。各步骤独立保存回执；等待某个投递动作审批不等于暂停整份计划，明确暂停任务仍保留暂停状态。

## 沟通话术

`DeliveryAutomationService.create_preview()` 是所有新预览的统一入口：

1. 读取当前已确认主简历及岗位 JD，只投影少量非联系方式摘录。
2. 模型选择一组已有的 JD / 简历摘录索引；应用验证索引、据原文定稿。模型没有生成资历、业绩或证书的权限。
3. 模型不可用或超过 3 秒时使用有依据的模板；不阻塞整批沟通，也不将降级记为模型完成。
4. 消息正文、引用、生成方式和简历摘要进入逐岗预览，绑定一次性授权。预览页面可查看定稿。
5. 在模拟站现有聊天输入框发送这份消息。已存在沟通、刷新、等待 HR 和重启时不再生成或重复发送；响应丢失只读取核验。

正常流程仍为逐个快速发起沟通、各岗位同时等待 HR，收到回复并核实按钮解锁后发送已授权简历。没有修改模拟站招聘方回复、申请条件或简历发送规则。真实网站沟通和投递保持禁用。

## 面试准备

在岗位详情点击“预测面试问题”，或在对话指定岗位生成。工具为：

- `interview_preparation_generate(selector, snapshot_id?, target_step_id?, focus?)`
- `interview_preparations_read(report_id?, limit?)`

后端提供受现有服务认证保护的 `GET/POST /api/v1/interview-preparations` 及单报告读取接口。前端通过同源服务端代理访问，不下发后端 Token。

模型按最小化简历事实和 JD 选择问题类别与原文依据，应用渲染问题、追问及准备要点。所有引用必须能在输入中找到；格式或引用有误时，最多修复一次，整个生成预算为 35 秒。Mock 模式明确展示模板建议。

报告在私有目录 `private/interviews/` 加密保存，绑定岗位、JD 指纹、主简历 ID、版本及摘要。后续简历或 JD 改变时显示旧快照提示。清除历史同时清除这些报告。

这是一份准备建议，不是招聘方真实题库、能力认证或录用概率预测。停止网页等待只取消等待响应，后台可能仍在生成；刷新可以核对是否已保存，不自动重发生成请求。

## 验证及重跑

从 `autohunt/agent/` 执行，需已安装项目开发依赖和 Playwright Chromium：

```powershell
.\.venv\Scripts\python.exe -m evaluation.workflow_upgrade_acceptance --browser --ui
```

该入口依次运行工程契约、状态驱动的多轮场景、真实 HTML 的拦截浏览器及隔离前端检查。使用临时数据库和虚构材料，不读取 `.env`，不调用外部模型，不操作现有招聘站账号。结果及源码指纹保存在忽略的 `evaluation/results/workflow-upgrade/`，逐场景轨迹在相应子套件目录。

多轮语料为 `evaluation/corpora/scope-chain-v1.json`，覆盖搜索扩展、投递条件更新/继承、单岗例外、旧回执与新搜索并存、追加成长计划及面试、暂停、重启和未知结果。不同介入阶段使用相同业务不变量检查队列、审批、数据库及回复。基础场景数和阶段矩阵数分开报告，脚本计划测试不充当模型理解准确率。

真实模型评估使用 `evaluation.scope_chain_model` 和 `evaluation.feature_model_probe`。需要单独授权目的地、合成数据和物理请求预算，修复、失败及语义复核调用均计入。可以重放保存的模型响应来定位规划与执行问题，重放不计作新的真实模型成功。

### 本轮发现的问题

| 问题 | 定位与处理 |
| --- | --- |
| 面试初测4例均返回 HTTP 400 | JSON 模式缺少格式关键词；修复服务提示，并在 DeepSeek Provider 的 JSON 模式统一加入格式约束。依据 [官方 JSON 模式文档](https://api-docs.deepseek.com/guides/json_mode/) |
| 等待确认卡后不推进 | 模型把动作等待审批规划为全局暂停；明确两者控制语义，保留真实暂停能力 |
| “其余岗位按原条件投”丢失旧条件 | 执行器把所有选择器视为独立范围；改为遵守显式 `inherit/update`，补契约与失败响应重放 |
| 审批后 `target_step_id` 无法续接 | 后台运行缺少读取本运行计划的接口；绑定持久化运行账本并验证审批后的目标读取 |
| 新搜索影响旧投递和分析 | 全局筛选缓存与回执耦合；队列和分析分别保存该轮的证据与事实绑定 |

工程、模型、HTML 浏览器与完整站点闭环分别记录结果。本轮不把离线通过数换算成自然语言泛化能力，也不把拦截页面的浏览器测试称为真实网站验收。最终数字见同目录的评测结果报告和 CI 记录。

## 本轮模型记录

累计使用 **39/40 次物理请求**：多轮规划 27 次，沟通/面试专项 12 次，未执行招聘操作。

- 多轮首轮为六组两轮会话：六组均可编译，原始测试中三组通过所有断言；失败包含真实接口问题和测试 oracle 对合法计划形式的误判。三条失败方向均保留原响应并完成修复后定向验证，部分复用已保存的第一轮。不能将其写成六组全新重跑后的准确率。
- 沟通专项四例均有可核对话术：三次模型完成选证据，一次超过默认 3 秒而使用模板回退。
- 面试初测四例均 HTTP 400；修复后四个行业各复测一次，四例通过。初始失败不从日志中删除。
- 多轮规划账本报告 664,987 输入 token、5,263 输出 token。完整工具 schema 与运行计划占用了较多输入，应将此作为后续上下文成本优化的基线；当前没有“低成本”的测量结论。
