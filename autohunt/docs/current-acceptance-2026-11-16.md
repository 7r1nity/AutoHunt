干净验证使用 Git 索引导出的源码副本和新建 Python 3.12 虚拟环境；没有 `.env`、用户数据库、浏览器 profile 或旧模拟站。按约束安装依赖，前端按 `pnpm-lock.yaml` 安装。73 项契约测试通过；脚本模型浏览器对照共 6 次通过。73 是 unittest 执行数量，包含既有继承用例，不等于 73 个独立用户任务。

每日 UI 链使用 Mock 模型、真实前端/API/浏览器和隔离站点，检查测试按钮、模拟 MFA、沟通等待、恢复不重发、绑定简历提交、提交后中断核验、完成不重放、错过四天合并补跑及历史页。这是一条链的 9 项检查。中断通过取消并重建对象实现，不是进程强杀/断电实验。

初次集成验收把 UI 输出放在新目录，旧历史页断言却读到了旧报告。因此该轮 `history_report_ui=true` 不作为本轮报告加载的有效证据。修正后输出到已有报告目录并强制核对本次精确报告 ID，再在干净副本复跑；原始记录保留，不覆盖。最终复跑结果见机器汇总的 `clean_reproduction`。

## 失败定位与边界

`resume_search` 的第一轮要求“先暂停不要执行”，但返回的新计划没有暂停标志，搜索步骤 `user_requested=true`。执行轨迹出现一次 `job_search_start` 合成工具调用，说明失败不是仅显示字段不同；第二轮“继续”后条件仍正确，但不能抵消第一轮提前执行。

这定位了 `plan_request → advance` 验收入口的行为缺口。未在本轮测试完整自然语言聊天路由对该输入是否有额外拦截，因此不能外推为所有入口都会提前搜索，也没有发生真实招聘站搜索或投递。后续修复应覆盖新建计划的延迟执行语义及实际聊天入口，而不能只给评分器补 `paused=true`。
