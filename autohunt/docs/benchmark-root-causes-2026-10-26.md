# 评测失败的源码定位与修复方案

本报告基于提交 `cc59eb7` 的生产源码和上轮保存的模型原始响应、验证反馈、计划及浏览器记录。本次只做离线复现与文档修正，未调用外部模型、未修改生产代码、未启动搜索或投递。

## 1. 条件 Schema 不一致：确定性接口缺陷，优先修

位置：`agent/app/core/job_filters.py` 的 `filter_schema`（85行）与 `FilterExpression.bounded_tree`（39行）；`agent/app/workflow/revision.py`（124行）和 `workflow/planning.py`（301行）将运行时异常转为修复请求。

给模型的 JSON Schema 用同一个对象表示所有节点，允许每个节点同时填写 `op/text/mode/salary/children`。运行时却规定：condition 不得有 children；all/any/not 不得有非空 text、salary 或非 require 的 mode。

最小离线复现：`{"op":"all","text":"组合描述","children":[{"op":"condition","text":"Python"}]}` 通过公开 `filter_schema()` 的 JSON Schema 校验，却被 `validate_filter()` 拒绝。condition 携带非空 children 也有同样差异。

真实记录：物理调用194—197（`salary_or`）的组合节点持续带有解释性 text，如“正式岗位且月薪至少15000元或面议”；199—202（`quota`）的 not 节点带有 text“外包岗位”。不是子条件必然缺失，而是组合节点的文字注释被运行时视为非法字段。重试三次仍保留同样字段。

修复方案：

- 用同一套节点定义生成模型 Schema、运行时类型及持久化规范，不再手工维护宽松 Schema 和严格 Pydantic 的两套契约。区分条件叶节点、组合节点、否定节点，明确各自必填项和子节点数量。
- 组合节点说明单独作为 annotation/label，不承载筛选约束。兼容旧输出时保留该说明为元数据，不随意删除、提升或改写子条件；说明与子树矛盾则交语义复核，不能盲目剥离。
- 模型输出支持受约束结构时接入；不支持时仍使用同一 Schema 的本地检查。受约束输出不能替代用户意图核对。
- 新增模型 Schema 与运行时接受域的双向契约测试，以及规范化前后真值等价测试，包含嵌套 all/any/not、空节点、深度限制和旧版数据读取。

验收：本轮完整 `salary_or`、`quota` 候选应能保留全部有效条件进入编译，或得到明确指出缺失/矛盾子条件的局部追问；不能再仅因组合注释重复调用模型。非法空 not、条件叶含子节点等仍不得执行。

## 2. 薪资范围扩张：先是模型误解，再被系统接受

需纠正此前表述：`count_inheritance`、`city_replace`、`append_growth` 三例的错误在**第一轮规划**已经出现，不是第二轮修改数量/城市或追加成长计划造成的。

证据：调用181、184、189的原始用户请求只有“月薪15k以上”，模型响应却已生成 negotiable 分支。181和184首次还包含非法条件结构；182、185修好了结构，但保留了擅自新增的面议分支。第二轮183只更新 result_limit；190只追加成长计划，并未重新改写原搜索条件。因此修改合并本身并非这三例的首发根因。

相关代码：`workflow/planning.py:185`、`:219` 的提示含月薪或面议例子；`:670` 之后修复只解决结构契约。`core/salary_conditions.py:112` 允许完整薪资树优先于旧 salary_min，是为支持合法 OR；这里不能简单改成把所有条件再 AND 最低月薪，否则会再次破坏合法实习/面议分支。

已证实：模型无依据加入条件，结构有效后应用接受。尚未证实：是否由提示示例诱导。判定具体提示因果需要新的、有预算的对照试验，不能仅凭日志断言。

修复方案：

- 当前需求保存为带来源轮次、版本和适用分支的结构化需求；后续修改默认输出增量 patch，未修改字段由程序继承，不让模型重写整份条件。现有修订已部分支持该做法，应保留。
- 首次解析或确实新增/扩大条件时，对“候选需求是否增加了用户未提出的接受范围”做独立、只读语义复核；输入仅为当前有效用户需求、旧需求和变更，不重新审查每个工具的原话授权。无法确定时追问该分支，保存其余任务。
- 复核不是新的绝对正确来源；记录判定与来源，测量误报/漏报。账号、文档绑定、一次发送和未知副作用核验继续由确定性授权负责。
- 用事实样本集验证范围：数值薪资边界、面议、未知、正式/实习独立日薪等；同时测“允许增加”的反例，不能把所有范围扩大都拒绝。

验收：原请求只给数值月薪时不能悄悄接受面议；明确允许面议、修改既有条件或新增实习分支时能正常生效；只改城市/数量不改任何未指定条件。首次误解与后续继承分别评分。

## 3. 组合岗位引用误拦截：限定词比较与 fallback 分类有缺陷

位置：`runtime/dialogue.py:422` 把序号后的整段 qualifier 作为一个字符串，要求它包含在单个 title 或 company 内。`core/job_targets.py:78` 遇到带序号的解析失败立即抛 TargetClarification，不进入后面的语义解析。

最小复现：快照只有岗位42，title=虚构Python后端工程师、company=合成雇主。

| selector | 生产函数结果 |
|---|---|
| 第1个 | 岗位42 |
| 第1个 虚构Python后端工程师 | 岗位42 |
| 第1个 合成雇主 | 岗位42 |
| 第1个 虚构Python后端工程师 合成雇主 | 误报不一致 |
| 第1个 错误公司 | 正确要求核对 |

三个浏览器失败 trial 正好使用第四种写法。不是浏览器变更、HR 延迟或授权过期导致，也不是模型选择了另一个岗位。

修复方案：

- 岗位引用采用同一个结构化对象：snapshot_id、ordinal、title/company/location等限定字段。详情、移除、单独投递和批量选择共用解析，不再各自补 selector 字符串规则。
- 序号先在不可变快照定位唯一岗位；限定描述只核对这个岗位。不能为了满足描述切换成其它序号。
- 区分越界、快照失效、明确事实冲突、尚未解析的组合限定词。前三类保留核对；后一类可以仅针对已锁定对象做语义核对。不是对所有序号错误开放无条件 fallback。
- 兼容旧字符串时保持原始指令、序号和分字段证据，避免模型拼接的解释文字被当成用户新增限制。

验收：表中前四种均定位42；第五种继续追问。跨快照、错公司、重复名称、中文公司名含数字、多个分支序号不得误选；发送与移除必须核验相同目标集合。

## 4. 页面适配与执行状态：能停止，但缺少下一步恢复

位置：`delivery/mock_site_adapter.py:80`、`:276` 硬编码 `#resume-btn`；`:262` 的 submit 一次点击后只轮询回执，不观察可完成的新步骤。`delivery/automation.py:402` 在调用 adapter.submit 前已设置 submit_started，此时适配器内部仍有只读预检；部分尚未点击的失败也可能被归为结果未知。当前 `workflow/failure_recovery.py` 的模型修复只用于特定只读工具错误，不会自动修复浏览器提交过程。

真实记录：按钮ID变化后，inspect既不能认出按钮，也不能判定正常等待HR回复，沟通阶段转 communication_unconfirmed；新增确认步骤时已有点击但未产生申请，最终 submission_unconfirmed。后者不能通过直接再点发送解决。

修复方案：

- 固定站点 adapter 增加控件定位策略：稳定属性→同一申请表单中的角色/名称组合；找到多个或语义不明时不点击。无需立即引入任意网页操作Agent。
- 页面观察返回明确状态：等待HR、缺控件、加载中、待补信息、新确认步骤、已提交、验证接管。缺控件不应隐含为“HR尚未回复”。
- 在真正发送尝试前的 callback 才持久化 effect_started，区分“预检失败且未发送”与“可能发送但未核实”。保留账号/简历/岗位绑定和一次发送约束。
- 控件变化或前进步骤先做有限只读重观察；确需辅助操作时只允许同一岗位和表单范围内的已分级动作，不能生成新投递授权。无法判断副作用时人工接管。
- 点击后无法确认先只读对账；确定已提交则补记，不能观察到记录不等于证明未发送。只有明确确认未提交且可安全继续时才处理新增步骤，禁止盲重放。

验收：按钮位置/名称/ID变化不误点其它控件；可完成确认步骤要真正产生正确申请；未知必填信息继续追问；响应丢失不重复提交。分别记录恢复完成、合理等待和待核验，不能混为成功。

## 5. 匹配信息缺口：输入契约缺失，不能靠评分提示弥补

位置：`core/models.py:150` 的 JobAnalysisRequest 无学历、年限、项目证据字段；`browser/screening.py:177` 发给模型的仅技能、方向、排除词与JD。候选人未传入的资历无法核对。这里只是确认匹配接口信息不全，不能据此断言其它独立筛选器也全部缺少这些事实。

方案：向匹配器传入经过用户确认、带来源和未知状态的候选人事实；硬条件结果与相关性评分分别输出，匹配分不得覆盖已确认的硬条件不满足或把未知变成满足。沿用现有证据/条件判定能力，避免再建一套平行规则。用跨行业、年限/学历反例及人工复核数据验证。

## 实施顺序与回归要求

1. 统一条件节点契约与错误路径；消除“公开Schema允许、运行时拒绝”的矛盾。
2. 统一岗位引用并区分真正冲突和可解析限定词；修复确定性误拦截。
3. 修正投递阶段和副作用标记，再补有限页面恢复；保留未知发送禁止重放。
4. 改善首次需求理解和条件扩张复核，补全匹配候选人事实。

每项先冻结本轮失败输入、原始模型输出和环境记录，再修改；先零模型回放检查工具/Schema/执行契约，再对需要语义判断的场景做真实模型验证。旧失败不得被新抽样的成功覆盖。相同场景需多次重复，还要加真实冲突与合法扩大范围的负例，观察最终数据库、授权范围和任务状态，不只看返回文字。

本报告已精确定位上述缺陷，但尚未实施生产修复。它不保证所有自然语言表达都能零误解；可先消除确定性接口矛盾，再以独立模型评测衡量语义错误是否下降。
