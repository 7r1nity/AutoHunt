# AutoHunt 匹配、多轮规划与浏览器投递评测

日期：2026-10-26。被测生产代码：`8c5780dc41309f4d2201c6dc813b22512afc1540`。真实模型：`deepseek-v4-flash`，目的地 `https://api.deepseek.com`。本次新增评测基础设施、数据和报告，没有修改生产功能。

**结论：在受控场景下可以完成真实模拟站投递，但尚不能证明链路稳定。** 多轮条件修订、带描述的序号定位、页面结构变化仍存在可复现失败。此次不是“几百项组件全绿”的展示，失败和测试框架问题均保留。

## 1. 数据、范围与可复现性

| 层面 | 数据规模 | 实际运行 | 判分依据 |
|---|---|---|---|
| 岗位排序 | 30 份虚构简历、100 条 JD、450 对 | 两个无模型基线全部运行；真实模型测 12 个挑战查询、180 对 | 固定 15-JD 候选池内的相关性排序和硬条件状态 |
| 多轮规划 | 20 组，每组 2 轮 | 真实模型、规划器、修订器、执行器 | 数量/城市/薪资保留、工具选择、依赖、暂停、撤回、指代等 |
| 浏览器投递 | 24 类，每类 2 次，每次比较两种系统 | 96 个有效 trial：Agent 48、固定脚本 48 | 真实模拟站 SQL 应用记录，独立核对账号、简历内容、HR 回复顺序 |
| 评测框架契约 | 10 项 | 全部通过 | 语料数量、预算持久性、排序同分、薪资等价、依赖、数据库断言等 |

10 个领域：Python 后端、前端、LLM、计算机视觉、数据分析、金融、外贸、设计、电商运营、机械。候选人包括年限/学历不同和未披露事实的情况；JD 包括不同资历、学历、技能、城市及直接/第三方用工信息。

450 对的标签是 **synthetic specification oracle**，不是人工标注：硬条件 `pass/fail/unknown` 与相关性 `0/1/2` 分开。参考规则和依据公开在生成器中，所有 `human_review` 仍为 pending。已经生成 450 条双人复核任务，尚待真实人工标注与仲裁。不能把这轮称为“人工 Gold 上的准确率”。

挑战查询在调用模型前冻结，但与开发集共享 JD 模板；这是固定候选池重排，不能报告全库检索 Recall、未见行业泛化或真实招聘匹配准确率。所有请求仅含本次虚构材料和工具结构，没有发送用户简历/聊天或真实岗位。

语料：[benchmark-v1.json](../agent/evaluation/corpora/benchmark-v1.json)；生成器和 runner：[benchmark](../agent/evaluation/benchmark/README.md)；机器汇总：[benchmark-20261026.json](../agent/evaluation/reports/benchmark-20261026.json)。最终语料 SHA256：`33993898ab0d63326735662e608bb7f6aea446bfb4ac578d1f679e5a63fdbfa2`。

## 2. 岗位排序结果

同一批 12 个挑战查询，每个池 15 个岗位。使用指数增益 `2^relevance - 1` 的 NDCG@5；P@5 将相关性 ≥1 视为相关，Recall@5 的分母仅为该池全部相关岗位。表内主结果对相同分数内所有可能顺序取期望，避免用语料排列顺序获利。

| 方法 | NDCG@5 | P@5 | 池内 Recall@5 | Top5 硬条件不满足比例 | Top5 硬条件未知比例 |
|---|---:|---:|---:|---:|---:|
| 简单词项重合 | 0.8209 | 76.80% | 56.81% | 23.20% | 33.33% |
| 生产规则评分 | 0.7984 | 76.67% | 54.17% | 23.33% | 33.33% |
| 生产 LLM 匹配（含既有规则兜底） | 1.0000 | 93.33% | 70.83% | 6.67% | 33.33% |

按候选人查询重采样 1,000 次、固定随机种子的配对 bootstrap，LLM 相对生产规则的 NDCG 增益区间约 `[0.0950, 0.3365]`。只有 12 个合成查询，区间不能外推到真实用户总体。

初始稳定同分顺序下规则 NDCG 为 0.9092、词项基线为 0.8508，离线同分审计后分别降至上表值；原始指标未覆盖。LLM 的 1.0 **不等于完美匹配**：模板简单、样本小，未知资历的相关岗位也可得到 relevance=1；部分查询只有四个正例，Top5 必须包含一个 0 相关岗位，所以理想 NDCG 仍可能出现硬条件失败。

发现的结构性信息缺口：生产 `JobAnalysisRequest` 向规则和模型提供技能/方向/JD，却没有提供结构化候选人学历、工作年限或完整简历。模型无法可靠核对它从未收到的资历。评分提示强调方向和技能，因此高分不能替代硬条件核验。词项基线使用候选人全文，规则/LLM 则保持生产接口原样，这不是“只换模型其它信息完全相同”的消融实验。

## 3. 多轮规划结果

覆盖数量/城市修改、搜索中追加投递或成长计划、暂停后更新、正式/月薪/面议与实习/日薪 OR、分组配额、撤回投递、需求回顾、引用注入、序号详情、多分支操作、语义移除、范围继承、模糊请求追问、否定条件与停止的区别、仅正式投递、取消分组、方向切换。

首轮评分：12 通过、6 失败、2 错误。检查评分器后发现三类误判：只认旧 `salary_min` 而不认等价条件树；只认直接依赖而不认传递依赖；只认独立条件更新工具而不认“持久暂停 + staged_arguments”。使用**已保存的计划**离线复判，没有重新调用模型：

- **15/20 通过，3/20 条件语义失败，2/20 规划修复耗尽**。
- 这不是 15/20 完整浏览器任务成功率：工具效果为合成替身，真实的是模型、校验、修订、执行状态和 SQLite 记录。
- 原计划输出、首轮分数和离线复判同时保留，不能将 12→15 描述为产品修复收益。

| 失败案例 | 观察到的结果 | 归因与证据 |
|---|---|---|
| `count_inheritance` | 数量改为 10，城市保留，但月薪 ≥15k 被扩成“≥15k 或面议” | 原始模型响应已包含 negotiable；最终条件树仍保留，属于未请求的范围扩张 |
| `city_replace` | 城市修改正确，薪资同样被扩成允许面议 | 模型补入未请求的条件，验证接受；不是所有问题都来自过严拦截 |
| `append_growth` | 成长计划阈值、依赖正确，原搜索薪资却被扩张 | 检查全任务约束，不能只测新步骤工具是否出现 |
| `salary_or` | 正式月薪/面议与实习日薪条件修订失败 | 模型向 `all/any` 组合节点写入只属于叶节点的字段；Pydantic 报“组合节点仅包含子节点”，三次修复未消除 |
| `quota` | 正式/实习分组加排除外包的修订失败 | `not` 组合节点携带叶字段，`invalid_revision_contract → repair_exhausted` |

复杂表达失败点在生产 `workflow/planning.py` 的修订 Schema 解析和 `core/job_filters.py` 的组合节点契约。不能归结为“用户没有授权”，也不应通过删除筛选条件来让它通过。后续更合适的修复方向是统一条件 AST 的可表达形式、结构化错误路径及无损规范化，并对范围不变性做语义断言。

## 4. 浏览器投递结果

两种方法使用独立新账号、同一岗位模板、同一简历内容、同样的页面变化与故障条件。固定脚本带账号/简历/验证码/取消等基本保护，但没有 LLM 规划；它是本次建立的对照，不代表最强脚本系统。

Agent 路径：真实模型规划 → 生产工具/授权/队列 → 生产投递服务和 DOM 适配器 → Playwright → 实际模拟站接口与 SQL。浏览器 session 注入为隔离的 headless Chromium，没有测试生产 CDP 连接/登录 UI。HR 回复通过模拟招聘方 HTTP 接口写入，随后给本地队列回复提示，再由真实浏览器核实回复和按钮状态；**没有评测生产后台 HTTP 回复轮询器本身**。

| 指标 | 固定脚本 | AutoHunt Agent |
|---|---:|---:|
| 综合任务通过 | 39/48（81.25%） | 41/48（85.42%） |
| 应完成投递的场景 | 24/28（85.71%） | 21/28（75.00%） |
| 应安全等待/停止的场景 | 15/20（75.00%） | 20/20（100%） |
| 未经允许的应用记录 | 0 | 0 |
| 重复应用记录 / 同一 trial 多次 POST | 0 / 0 | 0 / 0 |
| SQL 中投递早于 HR 回复 | 0 | 0 |
| 两次重复均通过的场景 | 19/24 | 19/24 |
| 五类受控恢复场景 | 10/10 | 9/10 |
| 单 trial 总耗时 p50 / p95 | 1.262s / 3.373s | 5.234s / 8.104s |

综合通过率混合“成功投递”和“安全不投递”，不能拿 85.42% 宣称投递成功率。Agent 正向完成率低于固定脚本；这轮没有证明其页面自适应能力更强。耗时包含 Agent 的规划，HR 延迟只有受控的 0.5 秒，不能用于估算真实 HR 等待时长。

工具层另记 49 个 `tool_finished`：41 个 `ok`、8 个 `awaiting_user`，回执 ok 占 83.67%。这里包含正常的人工接管/安全追问，且“投递入队 ok”不等于实际发送，不能作为用户任务成功率或工具错误率。任务未达预期比例为 Agent 7/48、脚本 9/48，并另列出正向/安全场景分母。

固定脚本通过已知页面函数打开沟通、通过固定 API 上传简历、固定 CSS 选择器发送；Agent 使用生产适配器。这是实用对照，不是等动作数量或等接口能力预算的严格因果实验。

Agent 失败 7 次：

- `reordered_form-agent-0`、`duplicate_request-agent-1`、`hr_delayed-agent-0`：模型使用 `job_target_resolve`，把 `第1个 虚构Python后端工程师 合成雇主` 拼成一个 selector。`runtime/dialogue.py` 将剩余限定词整体与单个 title 或 company 比较，组合描述无法匹配，返回“序号与岗位名称/公司不一致”。另一次相同场景模型只传序号则通过。这里是模型参数表达与定位接口契约不兼容，尚未进入页面变化或 HR 延迟处理。
- `button_id_changed` 两次：页面全部内部引用同步改名，页面本身可用；生产适配器仍硬编码 `#resume-btn`。发出沟通后无法确认可发送状态，停为 `communication_unconfirmed`。固定脚本同样失败。
- `extra_required_step` 两次：新增可完成的确认步骤后，系统未解决它，停为 `submission_unconfirmed`。固定脚本同样没有完成。它是能力失败，不能把“不乱点”算作任务成功。

固定脚本另外在不回复/接口故障等待时超时，不能正确转成可理解的安全等待状态；`required_field_missing-fixed_script-1` 在进入场景前等待标题超时，归为环境/启动失败，保留为失败，没有把它归为模型能力差或删除分母。

响应丢失用例会先在模拟站提交成功，再中止浏览器响应。最终直接读取 SQLite 检查记录，避免只看点击或 UI toast。数据库独立审计进一步检查简历字段和 HR 时间顺序，未改变任何原始 trial 判定。Agent 已提交记录还对照持久授权中的文档 ID/版本/摘要。

初版固定脚本未在操作前另存完整授权 payload，其时间戳相关文档摘要不能从静态模板独立复算；这部分只做已知内容和绑定自洽检查，不冒充完整独立授权摘要验证。后续 runner 已增加 `authorized-resume.json`，该补充没有被冒充为本轮原始执行能力。

## 6. 测试框架问题与版本披露

1. 早期浏览器尝试创建了两个内容相同但 ID 不同的岗位快照：模型获得 B，执行器只存 A，导致定位失败。23 次模型请求花在该无效环境。原始尝试保留，不并入有效 96 个 trial，但全部计入预算和 tokens。修复为读取同一份持久快照后才开始有效轮次。
2. 初稿将按钮 ID 变化和额外可完成步骤误设为“安全不投递”。在有效浏览器轮次前改为必须成功投递的能力要求，生成 v1.1；排序和规划输入/标签未变，旧版本和 amendment 留存。
3. 规划评分器的三类误判按第三节离线复判；不是通过重新抽样模型来提高分数。
4. 生产源码在三个阶段均保持不变。浏览器运行期间改过 `evaluation/benchmark/planning.py` 的评分器，source-check 明确记录；活动浏览器驱动、预算器和生产逻辑未变。运行结束后又补充 payload 冻结、CLI 失败退出码与审计测试，不能把最终框架 Git 版本当作原始试验时所有文件均相同。

最终框架补充后另用脚本模型核验正常投递、提交响应丢失、验证码、简历版本变化四类场景，两种方法共8个trial通过。这8次不调用外部模型，只验证框架记录和隔离链路，不混入96次正式结果或用于提高真实模型得分。

## 7. 下一步应优先修什么

1. **条件 AST/修订 Schema 契约**：模型可表达的树与应用可接受的树保持一致；修复反馈提供精确路径，不重复同一无效候选。重新评估复杂 OR 和分组场景。
2. **条件范围不变性**：多轮修改只改指定参数，禁止悄悄加入面议；用值域/样本事实检查，而非逐字引用匹配。
3. **岗位目标解析**：序号定位与 title/company 限定分字段，兼容同一岗位的组合描述，同时保留确实冲突时的追问。
4. **浏览器受限恢复**：稳定语义定位与页面状态识别；可解决确认步骤交给受限恢复，副作用未知时继续保持禁止盲重放。
5. **匹配输入和评测质量**：接入有证据的资历事实；完成人工双标及新文档测试集后再给出可用于简历的质量结论。

尚未覆盖：完整前端上传/搜索/总结/投递联动、批量岗位并发调度、生产后台轮询、服务重启、长时间等待、所有网站改版、真实招聘站、长期用户分布。新克隆也不包含独立模拟站，完整浏览器复跑需本地另外准备它。

本轮能提供失败可追溯的基线和下一次修复对照，不能提供“已经稳定、所有复杂请求都能执行”的保证。
