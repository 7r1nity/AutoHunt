# 执行决策与范围确认（2026-10-12）

## 实际调用链

规则分类 → 小模型 → 主模型结构化理解 → 计划规范化/有限修复 → RunStore 权威计划 → DAG runner → AgentToolRegistry 动作决策 → 具体执行器 → 持久回执 → 无工具回答整理。

规则不提取岗位词或重新判定投递意图。MCP/function calling 只描述工具和参数，不签发权限。模型的 `user_requested` 是意图解释；应用将其与持久计划中的具体动作、参数及结果来源关联后保存范围记录。模型不能在工具参数中注入批准凭证，也不能调用确认接口。

## 决策职责

| 决策 | 使用位置与行为 |
| --- | --- |
| ALLOW | 符合策略，进入执行；或当前动作已有明确范围记录 |
| WARN | 引文改写、目标注释缺失等非执行缺陷；记录后继续 |
| REPAIR | 编码/schema 错误；执行前在原规划预算中有限修复 |
| REPLAN | 依赖环或证据来源错误；沿已有有限修复路径重建候选图 |
| CLARIFY | 必要业务信息缺失/真实歧义；保存请求，要求补充 |
| REQUIRE_APPROVAL | 动作合法但同意/范围待核对；保存 waiting_approval，等待后从原步骤接续 |
| DENY | 未知工具、实际撤回/取消、外部执行器账号/凭据/站点边界等；确认不能覆盖硬限制 |

`AUTOHUNT_APPROVAL_POLICY=risk`、`AUTOHUNT_APPROVAL_THRESHOLD=HIGH` 为默认。普通只读搜索是 LOW，已分类本地可逆操作是 MEDIUM，模拟投递和包含沟通的 dry_run 是 HIGH。明确请求的已记录范围满足 risk 策略，避免重复确认。UNKNOWN 总要确认，模型的 requested 标记不能自行放行；新写入工具必须显式分类。`always` 要求独立确认；停止/暂停始终立即处理。政策配置不能启用真实站投递或覆盖执行器的硬保护。

未确认的投递不再在规划层加一个全局问题，也不在修订/恢复层重复拒绝。它进入执行入口的持久化等待；无关分支继续，依赖分支等待。业务字段缺失的原请求澄清仍沿原上下文管理路径处理，并非所有 questions 都已变为可并行执行的局部步骤。

## 持久化与接续

`action_approvals` 自动增量建表，和运行数据库使用同样的内部无损序列化及可选加密。记录：运行/会话/步骤、规范化动作参数、结果来源、需要绑定时的简历 stamp、状态及同意来源。内部数据不经过文本脱敏。通用 `arguments_digest` 仍仅为兼容审计，不重新成为执行门。

确认请求只有 approval_id、conversation_id、approve；客户端不能提交替代参数。服务端重读当前步骤、比较范围及简历，并用事务处理确认。双击同一决定幂等；外会话、陈旧范围、已撤回或停止的任务不能批准。

等待发生在领取执行 claim 之前，不计成“可能已发送”。等待不占会话锁、模型槽或浏览器。页面有明确范围及确认/取消按钮；唯一待确认动作也接受“可以/同意/确认”等短答；多个动作或同时存在简历提案时要求选择。复杂范围修改仍交模型解释、修订原步骤，而不是补正则。工具循环的投机外部调用同样转为持久动作计划，确认后走统一 runner。

重启恢复等待记录；“继续任务”不能把 pending 自动改为 approved。终态任务子运行接续时迁移未完成步骤的确认记录，旧记录失效。已完成回执不重放；结果不确定的发送保持待核验。新计划指针和无关 revision 不撤销旧动作；仅实质变化的动作重新建立范围记录。

## 范围与副作用

搜索条件、投递条件、成长分析条件分别保留；投递仍使用 condition/all/any/not 和薪资结构化谓词，fail/unknown 不入队。等待 HR 的逐岗位执行记录不靠聊天轮次或任务 TTL 作废；短期预览在启动时消费为持久的一次性投递运行。后台回复是唤醒线索；实际发送仍核对账号、简历、回复和按钮。

审批记录允许执行一个已定义动作，不替代逐岗位预览/一次性凭证。队列唯一预留、原子授权、resume binding、验证码接管、重复发送及不确定结果保护继续由已有投递执行器负责。真实站提交继续关闭。

## 修订

计划 checkpoint 是权威来源，DST/当前计划指针是投影。修订提交用数据库 CAS；陈旧 watcher 不能覆盖新版本。追加、删除、编辑 waiting_approval 及 pending 步骤；明确后续指令可更新 requested。改变条件并追加结果消费者时补入证据刷新依赖。

`invalidated_steps` 仅刷新已完成的读取/分析：保留旧结果和回执，新增带 refresh_of 的节点，未执行消费者改为依赖新节点。投递、外部搜索及结果不确定的动作不得通过此接口重放。历史版本的审计保留为 revision_history 和运行事件；不是另建无限全量计划版本表。已出队、已沟通的投递按自己的持久执行记录继续；停止投递使用现有队列撤回入口。

## 验证与限制

运行 `python -m evaluation.approval_contract` 和 `python -m evaluation.command_recovery_contract --regression`；恢复矩阵为 `python -m evaluation.recovery_contract`。新测试跨越实际 registry、加密 SQLite、计划 runner、后台 watcher、修订、短答确认及服务重启，执行器使用合成替身。每轮结果和失败轨迹保存在本地忽略提交的 test-results，不提交运行数据。

这些测试验证程序执行契约，不证明任意模型表达都正确，也不等同于真实浏览器端到端投递。模拟站/真实网站页面变化和模型误解仍需要独立评估。本地 API Key 是应用的信任前提；会话检查不是完整的多用户账号权限系统。当前运行服务采用单进程调度和 SQLite 事务，未实现跨 Worker 浏览器 fencing 租约；本次没有引入 sandbox/multiagent 或宣称外部平台 exactly-once。
