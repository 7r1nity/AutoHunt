# 投递公平调度（2026-10-11）

## 原因与设计

本地调度记录显示，首个队列职位启动后，`submit_authorised_resume` 连续抢占每轮，另四个职位停留 `queued`。固定优先级加25秒冷却不能解决30秒轮询的饥饿：下轮冷却总已到期。问题在执行调度，不在自然语言理解或投递令牌。

使用 codebase-design 的设计思路把公平性集中在 `RuleEngine.step`，不向每个业务动作增加特殊分支：

- 正常已就绪规则按最久未服务选择；初次或同龄规则按优先级。冷却只控制频率，不承担公平保证。
- 安全升级可以显式抢占；正常恢复、回复监测、派发、站点同步和每日检查走公平轮转。保证只针对符合执行条件的正常工作，不覆盖持续安全抢占或等待验证的共享浏览器。
- 忙时只记录观察，不消费轮次；执行失败或无进展也记录已获得机会，让其他正常工作继续。规则选择沿用现有决策日志。轮转游标在内存，重启后重新按优先级开始一次，然后恢复公平轮转；队列和投递回执不在内存游标里。
- 回复检查每次最多尝试一个浏览器操作，使用持久化的 `last_checked_at` 排序。跳过无效绑定、已取消和还未到检查时间的记录；执行前保存尝试时间，异常不能让最旧的一条永久挡住其他会话。
- 新职位逐个打开并沟通，随后释放 worker；HR 长时间未回复仅保留等待记录。下一次到该会话的轮询机会再检查原授权，无需重复发消息或重新授权。
- 单次回复检查完成后读取持久回执，再统计成功或完成队列项，不把启动时的 view 当完成结果。

浏览器仍只有一个操作执行槽，不并行点击。每轮有新任务和回复等待时两者均能获得机会，站点同步等其他正常工作也可以穿插。当前默认监测周期约30秒；每轮单会话检查意味着大量等待时单个职位的检查间隔会增长，并非每个 HR 回复都能在30秒内处理。

投递预览、一次性凭据、简历和账号绑定、验证码接管、停止传播、不确定结果不重放保持原逻辑；真实网站提交仍禁用。本次不改变授权范围、不恢复已取消任务，也不添加未来未授权岗位。
