## 实验设计

- 数据：30份虚构候选人、100条虚构JD、450对配对，参考标签来自冻结合成规格；没有完成人工双人标注，不是人工Gold。
- 排序：规则和关键词基线覆盖450对；同一12个挑战查询各15个候选，共180对重新调用生产匹配器。使用当前接口中的技能、方向及有原文来源的最小化学历/年限事实，不发送完整简历。
- 执行：24种场景，固定脚本和Agent各重复两次，共96次浏览器试验。每次新建虚构账号、岗位、数据库与浏览器上下文；真实HTTP/SQLite确认结果，不触碰用户队列或现有模拟站。
- 多轮规划：20组两轮请求，走真实规划/修订/执行记录，工具效果为合成替身。它与浏览器投递成绩分开计算。
- 预算：本轮单独批准最多300次物理DeepSeek请求，含失败、修复和取消；所有阶段共用一个持久计数，不重置。

## 指标口径

| 指标 | 分子/分母或定义 |
| --- | --- |
| Precision@5 | 前5个中 relevance≥1 的个数 / 5，先对单查询计算，再宏平均 |
| Recall@5 | 前5个相关岗位 / 固定15个候选池中的全部相关岗位；没有正例的查询记未定义并单列，不补0或1 |
| NDCG@5 | DCG增益为2^relevance−1，按理想前5排序归一化；同分组内均匀随机排列取期望 |
| 高度匹配 Precision@5 | 前5个 relevance=2 的比例 |
| 硬条件失败@5 | 前5个合成参考标签 eligibility=fail 的比例；分数不能将它解释成满足 |
| 任务成功率 | 最终达到场景预期的次数 / 全部试验；包含正确等待/停止 |
| End-to-End Task Success Rate | 只在必须完成投递的正向场景计分，要求正确账号、岗位、授权简历后台记录且HR回复在前；边界从已选岗位指令到后台回执 |
| 步骤成功率 | 运行轨迹中 tool_finished.status=ok / 全部已观察到的tool_finished；保护性拒绝也属于原始non-ok，另用保护场景通过率解释 |
| 错误恢复率 | 注入响应丢失/沟通后页面刷新后达到正确最终状态的次数 / 这些试验次数；延迟容错另统计5类预注册场景 |
| 平均执行时间 | 单次试验从准备虚构环境到清理结束的墙钟均值，含本轮模型规划；同时给p50/p95 |

本次不是从前端上传简历、检索全站到投递的完整E2E，也不包含真实HR等待时长、真实站点或长期并发容量。固定候选池Recall@5不等于全站检索Recall。重复与共享模板存在相关性，置信区间只描述本样本的不确定性。

## 结果

本轮物理请求286/300次，全部阶段完成；未继续消耗剩余14次预算。排序180次、浏览器规划48次、多轮规划58次。响应中的模型名为 `deepseek-flash`。三阶段运行时源码完整性检查均无变动，应用源码未修改。

### 匹配与排序：同一12个查询、180对

| 指标 | 关键词基线 | 生产规则基线 | 本轮LLM匹配器 |
| --- | ---: | ---: | ---: |
| Precision@5 | 76.80% | 76.67% | **93.33%** |
| Recall@5（候选池内） | 56.81% | 54.17% | **70.83%** |
| NDCG@5 | 0.8209 | 0.7984 | **1.0000** |
| 高度匹配 Precision@5 | 43.47% | 43.33% | **60.00%** |
| 硬条件失败@5，越低越好 | 23.20% | 23.33% | **6.43%** |
| 资历未知@5 | 33.33% | 33.33% | 33.33% |

12个查询的Recall与NDCG均有定义，没有将无正例查询补为满分。同分排名取均匀随机排列的期望，避免数据集固定顺序占便宜。相对生产规则，NDCG差值为+0.2016；按查询bootstrap的95%区间为[+0.0950,+0.3365]，仅描述这12个合成查询。

NDCG满分不意味着全部岗位都匹配：4个查询的候选池只有4个相关岗位，强行取前5一定还含一个无关岗位；另外8个查询分别有8或10个相关岗位。小规模、模板化候选池也使理想排序较容易达到。表中使用原始匹配分排序，不是在看到答案后重新排列；硬条件失败/未知仍须由独立投递门槛处理。

匹配器单对平均耗时1.941秒，p50为1.875秒，p95为2.477秒。资历三分类与合成oracle一致176/180（97.78%）：52个fail全识别为fail，64个pass识别为pass，60个unknown保留unknown；另外4个oracle pass被模型判unknown。没有出现oracle fail被模型判pass。

这4个分歧均涉及跨行业“相关经验”：oracle只检查总年限，模型要求有目标行业相关年限证据。需要人工仲裁并改进下一版标注，而不是修改当前标签抬高分数，也不能直接把unknown解释为模型误拦截。

### 多轮规划与本轮失败

原评分器记录18 pass、1 fail、1 error；独立复核为**19/20通过（95%）**，保留原始记录不覆盖。

1. **真实浏览器任务失败：模型抄错快照ID。** `reordered_form-agent-0` 的原始模型请求带有有效岗位快照，但返回结构化selector将ID末尾改写。目标解析正确拒绝了不存在的快照，随后没有只读修复/应用绑定，停在核对；未开始网页投递。不能因为场景叫“表单重排”就归因给DOM适配。第二次试验成功，但没有替换第一次失败。建议让应用从请求已确认快照绑定机械标识，模型只返回序号/语义限定；真实陈旧快照或目标冲突继续要求核对。本轮未改应用行为。
2. **真实规划请求失败：模型接口连接错误。** `append_delivery` 的调用发生 `APIConnectionError`，保留为首轮失败。286次请求中1次物理请求错误（0.35%）。本轮没有用新的成功调用抹掉该失败。可进一步验证只读模型调用的有界重试和任务保存，但不能重放已产生副作用的操作。
3. **评分器误判：合法搜索来源继承。** `scope_inherit` 的投递没有复制filters，但保留了原搜索的非外包条件、城市、依赖及evidence_step。执行器会将该搜索task_id传入队列，队列只读该搜索中已核实通过的结果。新增隔离真实队列测试证明：不重复传filters时同搜索2岗可入队，另一搜索岗位不会混入。评分器现接受这种有绑定的等价执行，不接受无依赖、不同来源或显式跨范围选择。此项为零API离线复判，原fail保留，不能当成重新跑出一次模型成功。

多轮规划20组平均6.868秒、p50为7.029秒、p95为8.474秒，含两轮及范围复核。新增指标/来源契约17项通过；冻结旧模型输出20组回放通过，不计入本轮19/20的真实模型成绩。
