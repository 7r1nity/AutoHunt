# 多轮范围与任务链评测

`corpora/scope-chain-v1.json` 保存用户目标、初始状态、后续指令、阶段矩阵和预期结果。`scope_chain_contract.py` 将这些场景送入真实的规划校验、修订编译、DAG 执行、审批、恢复与加密 SQLite RunStore；不是另写一套分类规则来模拟这些模块。

## 覆盖范围

当前有 42 个基础场景、86 个阶段组合，包含九类：

| 类别 | 检查内容 |
| --- | --- |
| 搜索条件修改 | 城市、方向、数量、薪资、实习、面议、第三方与福利条件；待执行与正在搜索两个时机 |
| 投递条件修改 | 降低/提高/移除分数门槛，扩大/收窄城市和薪资条件，增加实习与福利、清空限制、独立批次和原批次补投 |
| 单岗范围例外 | 序号、名称、公司与结构化目标；批准/拒绝；例外不扩散到后续批次 |
| 完整任务链 | 搜索完成后总结、投递入队、成长计划、面试准备；初始暂停、分组配额、不同分支阈值 |
| 恢复与撤回 | 已完成不重放、效果未知不重放、准备阶段失败可恢复、只读失败、等待 HR、撤回分支保留独立分析 |
| 搜索来源隔离 | 新搜索与旧结果投递并存；模型虚构来源不能变成可信结果证据 |
| 已选对象的范围继承 | 显式 `inherit` 保留旧批次约束；缺省单岗选择保持独立 |
| 预选目标审批后接续 | `job_target_resolve → target_step_id → 人工审批 → 后台执行`；拒绝、重开存储、当前会话切换逻辑计划 |
| 已选对象扩大范围 | `selector + scope_mode=update` 降低门槛仍需审批；继承元数据由服务端记录，拒绝与重开存储均不能发送 |

场景数是工程参数组合，不能视为 86 条独立自然语言样本，更不能用通过率证明对任意复杂表述都能理解。

## 真实接口与替身边界

真实执行：`validate_draft`、`edited_plan`、`advance`、`activate_staged_searches`、`watch_plan`、`decide_approval`、`recover_plan`、岗位引用解析、投递参数物化和 RunStore。

合成适配器：浏览器搜索、招聘队列、HR 等待记录、JD 总结、成长计划正文和面试报告正文。队列保存实际收到的岗位 ID、分数和条件，但不会访问招聘网站或发送简历。这里测试的是范围与任务编排契约，不能由这些结果推断真实 JD 匹配质量、页面适应率、HR 监测成功率或招聘投递端到端成功率。

离线运行在临时数据库，显式禁止 socket 网络连接；不会读取用户材料、历史或 `.env`。

```powershell
cd autohunt/agent
.\.venv\Scripts\python.exe -m evaluation.scope_chain_contract
.\.venv\Scripts\python.exe -m evaluation.scope_chain_contract --family prepared_exception
```

Windows asyncio 需要可用的本地 socketpair。受限宿主可能需要允许本地进程运行，但测试期间仍禁止招聘/模型网络连接。

## 真实模型评测与重放

`scope_chain_model.py` 从这份语料抽取六组代表性两轮会话，调用真实 `plan_request`，继续使用相同隔离执行环境。规划、格式修复、语义修正和 scope review 均计入同一物理请求预算。它读取模型配置与凭据；发出的指令、岗位和状态全部新造。

分别报告三层结果：

- 契约：模型输出能否通过真实计划/修订编译。
- 语义：搜索和投递范围是否按预期保留或更新，例外是否仍限定在单岗。
- 执行：审批前不产生该范围的效果，审批后只处理目标，搜索完成后依赖才启动，已完成步骤不重放。

模型调用必须另有数据范围与预算授权，不能因为脚本支持就自动运行：

```powershell
.\.venv\Scripts\python.exe -m evaluation.scope_chain_model --models-consented --physical-limit 24
```

保存响应可零请求重放；原合成快照 ID 一并恢复，不能通过改写目标引用使测试通过：

```powershell
.\.venv\Scripts\python.exe -m evaluation.scope_chain_model --replay evaluation/results/scope-chain-model/<run>
```

`--warm-start <run>` 只复用已保存的第一轮规划，再在新的明确预算内调用后续一轮。日志分别计数 `physical_requests` 与 `replayed_responses`，避免把缓存重放当作新的模型样本。

## 诊断原则

每个离线场景记录原始指令、候选修订/规范化计划、逐步状态、审批快照、适配器实参、最终搜索条件和最终投递范围。报告还包含语料与源码 SHA256，并指出运行期间源码是否发生变化。模型记录额外保存原始请求/响应和真实 token 用量；全为合成数据，默认留在被 Git 忽略的 `evaluation/results`。

本轮测试曾找出以下可复现接线问题：

1. 模型把“等我在确认卡上确认”理解成整个计划暂停，导致审批通过后仍不能接续；等待审批与全局暂停应有不同语义。
2. 模型使用 `selector + inherit` 表示“其余岗位继续原条件”，scope review 也接受，但执行前物化曾因 selector 提前返回而丢失旧限制；模型与执行接口的契约必须一致。
3. 前台目标定位结果依赖 `plan_reader`，后台审批续接上下文曾缺少该读取接口，合法 `target_step_id` 因而无法恢复。
4. 服务端新增选择范围继承标记后，审批保存与审批结算的快照字段必须同步，不能让完整性检查误拒绝人工决定。

也保留测试自身的失败诊断：不能直接覆盖终态执行记录，后续请求应创建子任务；合法 `target_step_id` 不能被测试限定为只有 `selector`；等待单岗例外审批时，已经获得授权的其他独立分支仍可继续，不能要求所有队列为空。这些是夹具/oracle 修正，不能计成产品缺陷修复。

自然语言“第一份符合条件的岗位”还暴露了目标定位边界：模型复述整段文字时，无辅助模型的严格解析器可能将“符合条件”当成岗位属性。稳定序号应生成结构化 ordinal；若生产依赖语义定位模型，还需在独立预算下评估该模型，不能将本脚本禁用辅助模型的结果直接算作线上拒绝率。
